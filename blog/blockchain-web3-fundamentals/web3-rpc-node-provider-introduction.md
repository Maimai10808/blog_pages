# Web3 开发为什么一定要懂 RPC？

如果你写过 Web3 前端，大概率见过这样的代码：

```ts
const balance = await client.getBalance({
  address: "0x...",
});
```

它看起来非常简单：调用 `getBalance`，传入地址，然后拿到余额。

但这行代码背后发生的事情，并不简单。

你的电脑本地并没有以太坊主网的完整状态，也没有直接保存这个钱包的余额。真正知道余额的是远端的以太坊节点，可能在法兰克福，可能在弗吉尼亚，也可能在新加坡。

所以这行代码本质上不是一个普通的本地函数调用，而是一次远程调用。

也就是：

> RPC，Remote Procedure Call，远程过程调用。

理解 RPC，是理解 Web3 应用性能、稳定性和成本的关键。

---

## 一、什么是 RPC？

RPC 的全称是 **Remote Procedure Call**，中文叫**远程过程调用**。

简单来说，它的意思是：

> 让你像调用本地函数一样，调用另一台机器上的函数。

比如本地函数调用：

```ts
Math.max(a, b);
```

这个函数在你的电脑上运行，CPU 直接执行代码，结果很快返回。

但 Web3 里的这行代码：

```ts
await client.getBalance({ address });
```

表面上像本地函数，实际上它是在远程服务器上执行。

真实过程大概是：

1. 前端代码调用 `getBalance`；
2. 客户端库把这个调用打包成网络请求；
3. 请求通过网络发送到 RPC 节点；
4. 节点解析请求；
5. 节点查询区块链状态；
6. 节点把结果打包返回；
7. 前端拿到余额并展示。

所以 RPC 的核心作用是：

> 把“跨网络访问远程机器”的复杂过程，伪装成本地函数调用。

这是一种非常有用的抽象，但也是一种“有成本的抽象”。

---

## 二、为什么 Web3 特别依赖 RPC？

区块链本质上可以理解为一个巨大的共享数据库。

它有几个特点：

- 分布式；
- 只追加，不随意修改；
- 多节点共识；
- 具备拜占庭容错能力；
- 所有状态都记录在链上。

如果你想读取链上状态，比如余额、区块高度、交易记录、合约数据，就需要问节点。

如果你想写入链上状态，比如发送交易、调用合约、授权代币，也需要通过节点提交交易。

所以，对普通 dApp 来说，RPC 几乎是唯一入口。

无论你在做：

- 钱包；
- DEX；
- NFT 市场；
- 区块浏览器；
- DeFi 仪表盘；
- 数据分析面板；
- 链上游戏；
- DAO 工具；

从软件工程角度看，本质上都是一个 RPC 客户端。

它们都在不断向区块链节点发起 RPC 请求。

---

## 三、RPC 为什么影响 dApp 体验？

很多 Web3 应用慢，并不是前端写得差，而是 RPC 用得差。

RPC 会影响至少几个方面。

### 1. 应用响应速度

每次 RPC 调用都要跨网络。

如果节点离用户很远，或者节点响应慢，页面就会卡顿。

比如用户打开一个 DeFi 页面，页面可能需要请求：

- ETH 余额；
- 多个 Token 余额；
- 池子信息；
- 授权额度；
- 当前价格；
- Gas 价格；
- 用户仓位；
- 历史交易。

一个页面可能轻松发出几十次 RPC 请求。

如果这些请求没有优化，用户就会感觉页面加载很慢。

---

### 2. 项目成本

RPC 请求通常不是免费的。

很多项目会使用 Alchemy、Infura、QuickNode 等 RPC 服务商。每一次读取、每一次合约调用、每一次批量请求，都可能计入账单。

如果一个页面无脑发很多 RPC 请求，就会增加项目运营成本。

更糟糕的是，很多请求其实可以缓存、合并或减少。

---

### 3. 稳定性

RPC 节点可能会：

- 超时；
- 限流；
- 被 DDoS；
- 服务宕机；
- 网络抖动；
- 返回错误；
- 数据延迟。

如果前端没有处理好这些情况，用户可能看到：

- 余额显示 0；
- 页面一直转圈；
- 交易状态不更新；
- 数据突然消失；
- 操作失败但原因不明。

这些都会严重影响用户信任。

---

### 4. 扩展性

一个小 dApp 只有几百个用户时，RPC 问题可能不明显。

但如果有几万、几十万用户同时访问，每人打开页面都触发大量 RPC 请求，后端 RPC 层很容易被打爆。

所以 RPC 不是小细节，而是 Web3 应用能不能规模化的基础层。

---

## 四、RPC 调用背后发生了什么？

以 `getBalance` 为例。

你写的是：

```ts
await client.getBalance({ address });
```

但底层大概会发生这些步骤：

1. **序列化 Serialization**
   客户端库把函数名、参数、ID 等信息打包成一段标准格式。

2. **网络传输 Transport**
   这段数据通过 HTTP、WebSocket 或其他传输方式发送到远程节点。

3. **反序列化 Deserialization**
   节点收到请求后，把字节数据解析成它能理解的结构。

4. **方法分发 Method Dispatch**
   节点根据请求中的方法名，比如 `eth_getBalance`，找到对应处理逻辑。

5. **执行查询 Execution**
   节点读取本地维护的区块链状态，查出地址余额。

6. **返回结果 Response**
   节点把结果重新打包，通过网络返回给客户端。

7. **Promise 解析 Resolve**
   前端的 `await` 等待结果返回，然后继续执行后续代码。

所以，`await` 不是装饰品。

它代表这不是一个瞬间完成的本地调用，而是一个可能跨越网络、跨越地域、依赖远程节点响应的过程。

---

## 五、JSON-RPC 是什么？

Web3，尤其是以太坊生态，主要使用的是 **JSON-RPC**。

它是一种用 JSON 格式表达 RPC 请求的协议风格。

一个典型的 JSON-RPC 请求长这样：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "eth_getBalance",
  "params": ["0x...", "latest"]
}
```

几个字段含义如下：

- `jsonrpc`：协议版本，常见是 `"2.0"`；
- `id`：请求 ID，用于匹配响应；
- `method`：要调用的方法名；
- `params`：方法参数。

节点返回结果可能长这样：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": "0x..."
}
```

这里的 `id` 很重要。

因为客户端可能一次发送多个请求，返回顺序不一定和发送顺序一致。通过 `id`，客户端才能知道哪个响应对应哪个请求。

---

## 六、自己实现一个 RPC，其实并不复杂

从最基础角度看，一个 RPC 服务大概只需要几件事：

1. 一个 HTTP 服务器；
2. 能接收请求体；
3. 能解析 JSON；
4. 能根据 `method` 找到对应函数；
5. 能执行函数；
6. 能把结果用 JSON 返回。

伪代码大概是：

```js
const handlers = {
  add: ({ a, b }) => a + b,
  echo: ({ message }) => message,
  whoami: () => "server",
};

server.on("request", async (req, res) => {
  const body = await readBody(req);
  const rpc = JSON.parse(body);

  const fn = handlers[rpc.method];
  const result = await fn(rpc.params);

  res.end(
    JSON.stringify({
      jsonrpc: "2.0",
      id: rpc.id,
      result,
    }),
  );
});
```

这就是一个极简 RPC Server 的核心。

如果把 `add` 换成 `eth_getBalance`，并让服务器连接真实区块链节点，它就开始接近一个区块链 RPC 服务。

当然，生产级 RPC 远比这个复杂。

它还需要处理：

- 错误；
- 超时；
- 鉴权；
- 加密；
- 限流；
- 批量请求；
- 缓存；
- 重试；
- 连接池；
- 节点故障切换；
- 数据一致性；
- WebSocket 订阅；
- 交易提交状态。

但是核心思想并不神秘。

---

## 七、为什么需要错误处理？

一个 RPC Server 不能只处理成功情况。

可能发生的问题包括：

- JSON 格式不合法；
- 方法不存在；
- 参数错误；
- 节点内部错误；
- 请求超时；
- 服务不可用。

JSON-RPC 有标准错误结构，比如：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32601,
    "message": "Method not found"
  }
}
```

常见错误码包括：

- `-32700`：Parse error，JSON 解析错误；
- `-32600`：Invalid Request，请求格式不合法；
- `-32601`：Method not found，方法不存在；
- `-32602`：Invalid params，参数错误；
- `-32603`：Internal error，内部错误。

好的 RPC Server 必须返回有用的错误信息。

否则客户端只知道失败，却不知道为什么失败。

---

## 八、Batch 请求为什么重要？

JSON-RPC 支持批量请求。

也就是说，客户端可以一次发送多个 RPC 调用：

```json
[
  {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "eth_getBalance",
    "params": ["0x...", "latest"]
  },
  {
    "jsonrpc": "2.0",
    "id": 2,
    "method": "eth_blockNumber",
    "params": []
  }
]
```

服务器可以一次返回多个结果。

这样做的好处是减少网络往返次数。

但要注意：批量响应的顺序不一定和请求顺序一致。

所以每个请求都必须带 `id`。

客户端不能依赖数组顺序，而要用 `id` 匹配请求和响应。

这也是为什么 JSON-RPC 里 `id` 字段非常重要。

---

## 九、RPC 不只有 JSON-RPC

RPC 是一个大概念，JSON-RPC 只是其中一种实现方式。

常见方式包括：

- JSON-RPC；
- REST；
- gRPC；
- WebSocket；
- XML-RPC；
- SOAP。

它们并不是完全同一层级的东西。

理解它们，需要分成三个维度来看。

---

## 十、理解 RPC 的三个维度

任何远程调用方案，基本都可以拆成三个选择：

### 1. 接口模型：你怎么表达操作？

一种是 RPC 风格：

```text
调用一个方法：getBalance(address)
```

另一种是 REST 风格：

```text
对一个资源执行动作：GET /accounts/:address/balance
```

RPC 更像“调用动词”。

REST 更像“操作名词资源”。

---

### 2. 编码格式：数据怎么表示？

常见选择有：

- JSON：文本格式，人类可读；
- XML：文本格式，更啰嗦；
- Protobuf：二进制格式，更小更快；
- MessagePack：二进制格式；
- CBOR：二进制格式。

JSON 的优点是简单、好调试、浏览器友好。

二进制格式的优点是体积小、解析快，但调试不方便。

---

### 3. 传输方式：数据怎么送过去？

常见传输方式有：

- HTTP/1.1；
- HTTP/2；
- WebSocket；
- TCP；
- QUIC。

普通 HTTP 是请求—响应模式。

WebSocket 是长连接，可以让服务器主动推送消息。

gRPC 通常基于 HTTP/2，可以复用连接，并使用二进制 Protobuf 编码。

所以不要简单说“REST vs gRPC”或“JSON-RPC vs WebSocket”。

它们很多时候是在不同维度上做选择。

---

## 十一、REST 和 RPC 有什么区别？

REST 的核心是资源。

比如：

```http
GET /accounts/0x123/balance
POST /transactions
DELETE /orders/123
```

它强调：

- 资源用 URL 表示；
- 使用固定 HTTP 动词；
- GET 读取；
- POST 创建；
- PUT 更新；
- DELETE 删除；
- 请求是无状态的；
- 尽量利用 HTTP 缓存机制。

RPC 的核心是方法调用。

比如：

```json
{
  "method": "eth_getBalance",
  "params": ["0x123", "latest"]
}
```

它强调：

- 调用某个远程方法；
- 方法名在请求体里；
- 参数也在请求体里；
- 更像本地函数调用。

REST 的优势是非常适合资源型系统，比如用户、订单、文章、商品。

RPC 更适合动作型系统，比如：

- 获取余额；
- 估算 Gas；
- 调用合约；
- 发送原始交易；
- 查询区块；
- 订阅事件。

区块链操作天然更像函数调用，所以以太坊选择 JSON-RPC 是合理的。

---

## 十二、JSON-RPC 为什么适合区块链？

以太坊在 2015 年上线时，选择 JSON-RPC 有很强的现实原因。

### 1. 浏览器天然支持 JSON 和 HTTP

dApp 主要运行在浏览器中。

浏览器天然擅长发 HTTP 请求，也天然支持 JSON。

这降低了开发门槛。

---

### 2. 语言无关

任何语言都能生成 JSON，任何语言都能解析 JSON。

区块链是开放生态，需要不同客户端、不同钱包、不同节点实现都能接入。

JSON-RPC 足够简单，适合开放生态。

---

### 3. 不需要编译和代码生成

gRPC 需要 schema、编译器和生成代码。

而 JSON-RPC 不需要这些。

开发者可以直接用 `fetch` 发送请求。

这对早期生态非常重要。

---

### 4. 方法模型更符合区块链

区块链 RPC 方法本来就是一组动作：

- `eth_getBalance`
- `eth_call`
- `eth_sendRawTransaction`
- `eth_estimateGas`
- `eth_blockNumber`

这些都更像远程函数，而不是传统 REST 资源。

---

### 5. 人类可读，容易调试

JSON-RPC 请求可以直接在浏览器 Network 面板里查看。

开发者很容易看到请求方法、参数和返回值。

这对开放生态很重要。

---

## 十三、JSON-RPC 的代价

JSON-RPC 好用，但不是没有成本。

### 1. 数据冗余

JSON 是文本格式，字段名要反复出现。

比如：

```json
{
  "jsonrpc": "2.0",
  "method": "eth_call",
  "params": [],
  "id": 1
}
```

每次请求都要带这些字段。

以太坊里很多数字还用十六进制字符串表示，也增加了体积。

---

### 2. 解析成本高

服务器需要把 JSON 字符串解析成对象。

当每天有数十亿次请求时，JSON 解析会消耗大量 CPU。

单次看起来不多，但规模一大就是成本。

---

### 3. 缺少类型安全

JSON-RPC 没有强 schema。

如果你写错方法名：

```json
{
  "method": "eth_getBalnce"
}
```

只有运行时才会报错。

如果参数传错，也可能运行时才发现。

这和 gRPC 不同。gRPC 有 `.proto` 文件，可以在编译阶段发现很多错误。

---

### 4. HTTP POST 不利于缓存

很多 JSON-RPC 请求都是通过 HTTP POST 发送。

对普通 HTTP 缓存层来说，POST 通常被视为可能改变状态的请求，因此不会像 GET 那样自然缓存。

但很多链上读取其实是可以缓存的。

比如某个历史区块的数据不会变，但因为它包装在 POST body 里，标准缓存层很难直接识别和缓存。

这导致 RPC 缓存变得更复杂。

---

## 十四、gRPC 为什么没有成为 Web3 主流？

gRPC 很强。

它通常使用：

- Protobuf 二进制编码；
- HTTP/2；
- schema 文件；
- 自动生成代码；
- 类型安全；
- 更小的数据体积；
- 更快的解析速度。

在服务端与服务端之间，gRPC 很适合。

比如一个公司内部的微服务调用，团队控制客户端和服务器，schema 可以统一维护，gRPC 非常高效。

但 Web3 不一样。

Web3 的客户端通常在浏览器里，调用的是公开节点。生态里有大量陌生开发者、钱包、dApp、脚本、工具，它们不一定共享同一套代码生成流程。

gRPC 的问题是：

1. 浏览器不能像普通 HTTP JSON 那样直接使用完整 gRPC；
2. 需要 schema 和编译步骤；
3. 调试不如 JSON 直观；
4. 更适合服务端内部通信；
5. 对开放、无许可、多语言生态不够轻量。

所以 gRPC 很强，但不是以太坊 JSON-RPC 这种开放浏览器生态的最佳默认选择。

---

## 十五、WebSocket 在 RPC 中是什么角色？

WebSocket 不是 JSON-RPC 的竞争对手。

它是传输层选择。

你可以运行：

```text
JSON-RPC over HTTP
```

也可以运行：

```text
JSON-RPC over WebSocket
```

HTTP 是客户端发请求，服务器返回响应。

WebSocket 则是建立一个长期连接，连接建立后，客户端和服务器都可以主动发送消息。

这非常适合实时数据。

比如：

- 钱包余额实时更新；
- DEX 价格实时变化；
- Gas 价格实时刷新；
- 新区块订阅；
- 交易状态推送；
- 链上事件监听。

以太坊里常见的订阅方法是：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "eth_subscribe",
  "params": ["newHeads"]
}
```

这个请求的 JSON-RPC 格式没变，只是传输方式换成了 WebSocket。

---

## 十六、WebSocket 的代价

WebSocket 解决了实时推送问题，但也带来新问题。

### 1. 长连接更脆弱

用户网络断开、切换 Wi-Fi、手机锁屏、服务端重启，都可能导致连接断开。

断开后需要重连。

---

### 2. 需要同步状态

如果连接断开期间错过了新区块或事件，客户端需要重新同步。

否则页面状态可能不准确。

---

### 3. 服务端连接成本更高

HTTP 请求结束后连接可以释放。

WebSocket 需要长期保持连接，服务端要维护更多状态。

所以 WebSocket 适合实时数据，但不适合所有请求都用它。

---

## 十七、为什么 2015 年选择 JSON-RPC 是正确的？

回到以太坊诞生初期，选择 JSON-RPC 是一个非常合理的决定。

因为当时最重要的是：

- 快速启动生态；
- 让浏览器 dApp 容易接入；
- 让不同语言都能实现；
- 让节点团队容易兼容；
- 让开发者容易调试；
- 降低工具链门槛。

JSON-RPC 正好满足这些要求。

它简单、开放、可读、语言无关、浏览器友好。

所以在 2015 年，JSON-RPC 是非常适合以太坊的选择。

---

## 十八、为什么今天 RPC 问题变严重了？

问题在于，2026 年的 Web3 规模已经不是 2015 年的规模。

现在的 dApp 可能每天处理海量请求。

一个页面可能发出几十个 RPC 调用。

用户可能在手机弱网环境下使用。

RPC 服务商按请求量、带宽或计算量收费。

这时 JSON-RPC 的问题就被放大了：

- 文本冗余变成带宽成本；
- JSON 解析变成 CPU 成本；
- 缺少缓存变成响应慢；
- 请求过多变成页面卡顿；
- 节点不稳定变成用户体验问题；
- WebSocket 断线变成同步问题。

所以，JSON-RPC 的历史选择没有错。

但今天的 Web3 应用必须学会优化 RPC。

---

## 十九、Web3 开发者应该重点关注什么？

如果你是 Web3 前端或全栈开发者，不应该只会写：

```ts
client.getBalance();
contract.read();
contract.write();
```

你还应该理解它们背后的 RPC 成本。

重点关注这些问题：

1. **能不能减少 RPC 请求数量？**
   不要一个组件发一次请求，能合并就合并。

2. **能不能批量请求？**
   多个独立请求可以考虑 batch。

3. **能不能缓存？**
   历史区块数据、静态合约信息、Token metadata 都可以缓存。

4. **能不能并发？**
   不要所有请求串行等待。

5. **能不能降级处理？**
   RPC 挂了时，不要直接显示余额为 0。

6. **能不能切换节点？**
   主 RPC 失败时，要有备用 RPC。

7. **实时数据是否应该用 WebSocket？**
   不要用轮询疯狂请求实时数据。

8. **错误信息是否明确？**
   用户需要知道是网络问题、节点问题，还是交易失败。

---

## 二十、总结

RPC 是 Web3 应用的基础层。

从表面看，`client.getBalance()` 只是一行普通代码。

但它背后涉及：

- 序列化；
- 网络传输；
- 远程节点；
- JSON-RPC；
- HTTP；
- WebSocket；
- 错误处理；
- 批量请求；
- 缓存；
- 超时；
- 节点稳定性；
- 成本和性能。

JSON-RPC 之所以成为以太坊主流，是因为它简单、开放、浏览器友好、语言无关、容易调试，非常适合早期生态启动。

但它也有明显代价：文本冗余、解析成本高、类型不安全、缓存困难、实时能力弱。

gRPC 更高效，但更适合服务端内部通信；REST 更适合资源模型；WebSocket 更适合实时推送。

所以，真正优秀的 Web3 开发者，不只是会调用 SDK，而是理解 SDK 背后到底发生了什么。

一句话总结：

> RPC 决定了 dApp 是丝滑还是卡顿，是省钱还是烧钱，是稳定还是经常崩。

如果你想把 Web3 应用做得像 Web2 一样流畅，RPC 不是可选知识，而是必须掌握的基础。
