# EIP-7702 详解：让 EOA 临时拥有智能合约能力，钱包体验会发生什么变化？

在过去，用户和 DeFi 协议交互时，经常会遇到一个非常典型的操作流程：

先 approve；

再 deposit、swap 或 supply。

也就是说，用户想把某个 ERC20 Token 存入协议，往往需要先发一笔授权交易：

```txt
approve(protocol, amount)
```

然后再发第二笔业务交易：

```txt
deposit(amount)
```

这不仅麻烦，也带来了一些安全问题。用户需要确认两次交易，也需要分别检查两次交易内容。时间久了，很容易产生安全疲劳。

Ethereum 的 Pectra 升级引入了 EIP-7702，正是为了改善这类钱包交互体验。它让普通外部账户 EOA 在一定条件下具备类似智能合约钱包的能力，从而支持批量交易、单次操作完成多步调用，以及更灵活的钱包逻辑。

## 一、EIP-7702 想解决什么问题

在传统 EOA 模型下，像 MetaMask、Ledger 这类普通钱包账户，本质上只是一个由私钥控制的地址。

它能做的事情相对简单：

签名；

发送交易；

转 ETH；

调用合约。

但它自己没有合约代码，不能像 Safe 这样的智能合约钱包一样，把多个操作打包在一起执行。

这就导致很多交互必须拆成多步。

比如用户想把 USDC 存入 DeFi 协议：

```txt
第一步：approve USDC 给协议
第二步：调用协议 deposit
```

再比如用户想给多个地址发送不同 Token：

```txt
给 A 转一笔
给 B 转一笔
给 C 转一笔
```

每一步都需要单独发交易。

虽然可以部署一个合约来批量处理这些操作，但这对普通用户并不现实。用户需要先把资产授权或转入合约，开发者还要部署额外逻辑，整体体验并不好。

智能合约钱包一直拥有批量交易能力，比如 Safe 可以一次执行多个调用。但 Safe 本身是合约账户，仍然需要某个 EOA 来发起或签署操作。

EIP-7702 的核心想法是：

让 EOA 在保持原有账户形态的同时，临时或持续地使用某段智能合约代码。

简单说，就是让普通钱包地址也可以拥有类似智能合约钱包的执行能力。

## 二、从 EOA 到 Smart EOA

传统账户大致分为两类。

第一类是 EOA，也就是 Externally Owned Account。

例如：

MetaMask 账户；

Ledger 地址；

普通私钥控制的钱包地址。

第二类是智能合约账户。

例如：

Safe 多签钱包；

自定义账户抽象钱包；

各种链上合约地址。

EIP-7702 引入了一种更像“混合形态”的账户：

它本质上还是 EOA；

但可以被授权使用某个合约的代码；

在执行时表现得像一个智能合约账户。

可以把它理解成 Smart EOA。

这个 Smart EOA 既保留了普通钱包的地址和签名能力，又获得了智能合约的批量调用能力。

## 三、EIP-7702 的直观效果

EIP-7702 最直观的变化是：原本需要两笔交易的操作，可以合并成一笔。

过去：

```txt
approve
  ↓
deposit
```

现在可以变成：

```txt
approve + deposit
```

在同一笔交易中完成。

例如用户想把 Token 存入某个协议，钱包可以通过 EIP-7702 让 EOA 使用特定的智能合约执行逻辑，然后一次性完成：

```txt
approve token
supply token
deposit token
```

再比如批量转账，过去可能需要多笔交易。现在可以把多个 transfer 打包在同一笔交易中执行。

这会显著改善钱包和 DeFi 应用的用户体验。

用户不再需要连续点击多个确认按钮，也不需要等待第一笔交易确认后再发第二笔交易。

## 四、Type 4 Transaction 是什么

EIP-7702 引入了一种新的交易类型，通常被称为 Type 4 Transaction。

这类交易中会包含一个 authorization list。

可以简单理解为：

```txt
我这个 EOA 接下来要使用哪一段合约代码？
```

也就是说，交易中会指定一个被授权的合约地址，EOA 会委托使用这个地址上的代码。

当用户发送这种交易时，钱包实际上是在告诉链上：

```txt
请让我的 EOA 使用这个合约地址上的代码逻辑。
```

之后，这个 EOA 就可以按照该合约代码的逻辑执行批量调用或其他智能账户能力。

## 五、授权代码不是只生效一次

有一个很容易误解的地方：EIP-7702 并不是让 EOA 只在当前交易中临时使用一次代码，然后自动恢复普通状态。

更准确地说，EOA 会保持这个代码委托状态，直到用户主动取消或切换到其他代码。

也就是说，一旦你的 EOA 被设置为使用某个 delegation code，它会继续保持这个 Smart EOA 状态。

你可以之后再发送交易，把它切换到其他代码，或者停用当前委托。

这点非常重要。

因为它意味着用户不是在“临时跑一段代码”，而是在给自己的 EOA 绑定某个执行逻辑。

如果绑定的是可信钱包提供方审计过的代码，通常问题不大。

如果绑定的是恶意代码，就可能非常危险。

## 六、EIP-5792 与 wallet_sendCalls

为了让钱包和 DApp 更好地使用这类能力，新的钱包交互标准也开始出现，例如 EIP-5792 中的 `wallet_sendCalls`。

它可以让网站向钱包请求一组调用，而不是只请求一笔单独交易。

比如网站可以请求：

```txt
调用 A Token 的 transfer
调用 B Token 的 transfer
```

钱包收到请求后，可以提示用户：

```txt
是否使用智能账户？
是否执行这批调用？
```

在支持 EIP-7702 的钱包中，用户可以把这些操作合并成一笔交易执行。

这就是为什么未来 DeFi 交互可能会从“先 approve 再 deposit”，变成一个按钮完成。

## 七、在钱包里会看到什么

以支持相关能力的钱包为例，用户可能会看到这样的提示：

```txt
Would you like to use a smart account?
```

或者类似：

```txt
Use smart account
```

这表示钱包准备让你的 EOA 以 Smart Account 的方式执行。

之后你可能会看到一个交易请求，其中包含多个调用。

例如：

```txt
Call transfer on Aave token
Call transfer on USDC
```

交易详情中可能会显示：

```txt
Account Type: Smart Account
```

这说明当前交易不是传统的普通 EOA 单一调用，而是使用了智能账户能力进行批量调用。

## 八、为什么交易中 from 和 to 可能是同一个地址

在区块浏览器中查看 EIP-7702 交易时，可能会看到一个很奇怪的现象：

```txt
from: 你的地址
to: 你的地址
```

这看起来像是自己调用自己。

原因是：你的 EOA 现在已经绑定了某段合约代码。它在执行时，相当于调用自己地址上的委托代码逻辑。

也就是说：

你的 EOA 地址没有变；

但它现在有了执行代码的能力；

所以交易看起来像是 EOA 调用了自身的智能账户逻辑。

在 Etherscan 这类浏览器中，你还可能看到：

```txt
Type 4 Transaction
Authorization List
Delegated Address
```

其中 Delegated Address 就是你的 EOA 当前使用的代码来源地址。

## 九、Delegated Address 是什么

Delegated Address 可以理解为：

```txt
我的 EOA 正在使用哪一个合约地址上的代码？
```

当你使用 EIP-7702 时，并不是把代码复制进你的账户，而是让你的 EOA 委托执行某个地址上的代码逻辑。

区块浏览器可能会显示这个被委托的地址。

例如某些钱包会使用自己开发并审计过的 delegator 合约。这样用户在使用 Smart EOA 能力时，实际上是使用钱包方固定好的安全执行逻辑。

这是一种比较保守也更安全的设计。

## 十、为什么钱包通常会硬编码 Delegator

从安全角度看，最关键的问题是：

谁来决定你的 EOA 使用哪段代码？

如果任意网站都能指定你的 EOA 委托给任意合约，那么风险会非常高。

恶意网站可以让你委托给一段恶意代码，然后在看似正常的交易中执行危险逻辑，例如转走所有 Token。

因此，一些钱包会选择硬编码 delegator 合约。

也就是说，DApp 不能随便告诉钱包：

```txt
请让用户委托给我的恶意合约
```

钱包只允许用户委托给钱包方自己提供、审计过、固定的智能账户合约。

这种做法会牺牲一点灵活性，但能显著降低普通用户被恶意网站欺骗的风险。

## 十一、EIP-7702 会不会让用户一笔交易丢掉所有 Token

理论上，可以。

如果用户把 EOA 委托给恶意代码，那么恶意代码可以在执行过程中做很多危险操作。

例如它可以在一笔看似普通的交易中，遍历用户的 Token 余额并尝试转走资产。

这也是很多人担心 EIP-7702 的原因：

```txt
以前可能要多次 approve 才能出问题；
现在是否一笔交易就能丢掉全部资产？
```

答案是：在恶意委托代码存在的情况下，确实可能。

但对于普通钱包用户来说，主流钱包通常不会允许网站随意设置 delegation code。钱包会使用硬编码、审计过的代码作为执行逻辑。

所以真正的风险主要集中在：

开发者自己构造底层 EIP-7702 交易；

高级用户手动委托到不可信合约；

钱包实现不安全；

DApp 或钱包没有清楚展示 delegation 信息；

用户盲签或盲发交易。

普通用户如果只使用主流钱包提供的默认 Smart Account 能力，并认真检查钱包弹出的交易内容，风险会小得多。

## 十二、为什么这仍然是 UX 的巨大进步

虽然 EIP-7702 带来了新的安全注意事项，但它对用户体验的改善非常明显。

过去 DeFi 用户经常要经历：

```txt
approve
等待确认
deposit
等待确认
```

现在可以是：

```txt
一次确认
完成 approve + deposit
```

过去批量转账需要多笔交易。

现在可以是：

```txt
一次确认
完成多次 transfer
```

过去想要智能合约钱包能力，需要部署 Safe 或其他合约账户。

现在普通 EOA 也可以在一定程度上拥有智能账户能力。

这对大规模用户采用非常重要。因为普通用户并不关心底层账户模型，他们只希望：

少点几次按钮；

少等几次确认；

少付不必要的 Gas；

交互更接近 Web2 应用体验。

EIP-7702 正是在往这个方向推进。

## 十三、EIP-7702 与 Smart Contract Wallet 的关系

EIP-7702 并不是完全替代 Safe 这类智能合约钱包。

Safe 仍然有自己的优势：

多签；

模块化权限；

复杂治理；

资产管理；

组织账户；

团队协作；

链上权限控制。

而 EIP-7702 更像是增强普通 EOA，让它具备一部分智能账户能力。

可以简单理解为：

Safe 是完整的智能合约钱包；

EIP-7702 是让 EOA 临时或持续使用智能合约逻辑；

二者可以共存。

对于个人用户，Smart EOA 可能更轻量。

对于团队、多签、DAO 和高价值资产管理，Safe 这类合约钱包仍然非常重要。

## 十四、开发者需要注意什么

对开发者来说，EIP-7702 带来了新的能力，也带来了新的责任。

### 1. 不要让用户委托到不可信代码

如果你在开发底层工具或钱包，不应该允许任意网站无提示地设置 delegated address。

### 2. 钱包必须清楚展示交易内容

钱包应该显示：

是否使用 smart account；

批量调用了哪些目标地址；

每个调用的 calldata；

是否设置或修改了 delegation；

delegated address 是谁；

该 delegated address 是否经过钱包方验证。

### 3. DApp 不应该隐藏授权逻辑

即使 approve 和 deposit 合并在一笔交易里，也应该让用户清楚知道：

授权给谁；

授权多少；

接下来执行什么操作。

### 4. 区块浏览器需要支持新交易类型解析

用户需要能看到：

Type 4 Transaction；

Authorization List；

Delegated Address；

批量调用内容；

实际 Token 转移。

这些信息对安全分析非常重要。

## 十五、普通用户应该注意什么

对于普通用户来说，使用 EIP-7702 相关功能时，可以记住几个原则。

第一，看到“Use Smart Account”时，要知道这是在启用智能账户能力。

第二，认真检查钱包展示的批量交易内容。

第三，确认每个 transfer、approve、deposit 是否符合预期。

第四，不要在不可信网站上启用 Smart Account。

第五，如果钱包显示 delegated address，尽量确认它是否是钱包官方合约。

第六，不要使用来路不明的钱包或签名工具。

第七，如果你是开发者，不要随便手动委托到自己不了解的代码。

第八，定期检查区块浏览器中账户的 delegated address 状态。

第九，高价值资产最好使用更严格的钱包策略，例如硬件钱包、多签、白名单等。

## 十六、EIP-7702 之后，approve 会消失吗

approve 不会消失。

ERC20 的授权模型仍然存在。很多协议仍然会继续使用 approve。

但用户体验上，approve 可能不再表现为单独一笔交易。

它可能会被打包进同一笔智能账户交易中：

```txt
permit / approve
deposit / swap / supply
```

这意味着用户感知上会少一次确认，但底层仍然发生了授权逻辑。

因此，安全检查仍然重要。

不要因为只点了一次按钮，就忽略这笔交易内部可能包含多个步骤。

## 十七、EIP-7702 的核心价值

EIP-7702 的核心价值可以总结为：

让 EOA 拥有智能合约执行能力；

支持批量交易；

减少重复 approve；

改善 DeFi 交互体验；

让普通钱包更接近智能合约钱包；

为账户抽象和更好的钱包 UX 铺路。

它不是单纯的性能优化，而是账户模型的一次重要演进。

过去 EOA 和智能合约账户是两种明显不同的东西。

EIP-7702 让二者之间出现了一种混合形态。

这可能会成为未来 Ethereum 钱包体验升级的重要基础。

## 十八、总结

EIP-7702 是 Ethereum Pectra 升级中的重要改进之一。它允许 EOA 通过新的 Type 4 Transaction 和 authorization list 委托使用某个合约地址上的代码，从而获得类似智能合约钱包的能力。

它解决的核心问题是：普通钱包交互太碎片化。

过去用户经常需要先 approve，再 deposit；或者为了批量转账发送多笔交易。EIP-7702 让这些操作可以被打包进一笔交易中，显著改善用户体验。

但它也带来了新的安全边界。因为一旦 EOA 委托给恶意代码，理论上可能在一笔交易中执行危险逻辑，甚至转走多个 Token。

因此，钱包实现非常关键。主流钱包通常会硬编码经过审计的 delegator 合约，避免网站任意指定恶意 delegated address。用户也需要认真检查钱包展示的批量调用内容，不要盲目确认。

可以把 EIP-7702 理解为：

```txt
让普通钱包地址获得智能合约钱包的部分能力。
```

它不会消除所有风险，也不会取代所有智能合约钱包，但它会让 Ethereum 钱包交互变得更接近普通用户能够接受的体验。

未来，越来越多网站可能会从“approve + deposit 两次点击”，升级为“一次确认完成多步操作”。这对 Web3 UX 来说，是一个非常重要的进步。
