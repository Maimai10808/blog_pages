# 一文理解 HTTP：从请求响应到 HTTP/1.1、HTTP/2 与 HTTP/3

## 1. HTTP 是什么？

HTTP，全称是 **HyperText Transfer Protocol，超文本传输协议**。它是 Web 世界中最基础、最常见的应用层协议之一。我们平时在浏览器中打开网页、加载图片、请求接口、下载文件，本质上很多时候都离不开 HTTP。

简单来说，HTTP 负责在客户端和服务器之间传输资源。这些资源可以是：

- HTML 页面；
- CSS 样式文件；
- JavaScript 脚本；
- 图片、音频、视频；
- JSON 数据；
- 二进制文件。

比如我们在浏览器中输入一个网址，浏览器会向服务器发送 HTTP 请求，服务器接收到请求后，再把对应的网页内容返回给浏览器。浏览器拿到 HTML 后，还会继续解析其中引用的 CSS、JS、图片等资源，并继续发起新的 HTTP 请求。

因此，一个网页的加载过程，往往并不是一次请求完成的，而是由许多次 HTTP 请求共同完成的。

## 2. HTTP 的基本模型：客户端与服务器

HTTP 采用典型的 **客户端—服务器架构**。

客户端负责发起请求，服务器负责处理请求并返回响应。

常见的客户端包括：

- 浏览器；
- 手机 App；
- 前端 JavaScript 程序；
- Python、Java、Go 等语言写的后端服务；
- 命令行工具，比如 curl。

服务器则运行着 HTTP Web Server，用于接收和处理请求。常见的 Web Server 包括：

- Apache；
- Nginx；
- IIS；
- Node.js HTTP Server；
- Python Tornado、Flask、Django 等框架提供的服务能力。

HTTP 的交互模式可以概括为：

> 客户端发送 Request，服务器返回 Response。

这也是 HTTP 最核心的工作方式。

## 3. HTTP 请求由什么组成？

一个 HTTP 请求通常包含几个关键部分：URL、请求方法、请求头和请求体。

### 3.1 URL

URL 用于告诉服务器：客户端想访问哪个资源。

例如：

```text
https://example.com/articles/http
```text

这个 URL 表示客户端想访问 `example.com` 服务器上的 `/articles/http` 资源。

URL 中还可以包含查询参数，例如：

```text
https://example.com/search?keyword=http
```

这里的 `keyword=http` 就是查询参数。

### 3.2 请求方法

HTTP 请求方法表示客户端想对资源做什么操作。

常见方法包括：

| 方法    | 含义                     |
| ------- | ------------------------ |
| GET     | 获取资源                 |
| POST    | 提交数据或创建资源       |
| PUT     | 更新资源                 |
| DELETE  | 删除资源                 |
| OPTIONS | 查询服务器支持的通信选项 |

可以用数据库操作来类比：

- GET 类似查询；
- POST 类似新增；
- PUT 类似更新；
- DELETE 类似删除。

例如访问一个网页时，浏览器通常会发送 GET 请求；提交登录表单或上传文件时，通常会发送 POST 请求。

### 3.3 请求头

请求头用于携带额外信息，例如：

- 客户端能接受什么类型的数据；
- 请求来自哪个 Host；
- 是否携带 Cookie；
- 浏览器类型和版本；
- 是否使用缓存；
- 内容类型是什么。

例如：

```http
Accept: text/html
User-Agent: Chrome
Cookie: token=xxxx
Content-Type: application/json
```http

请求头不直接表示资源内容，而是用来描述请求的上下文。

### 3.4 请求体

请求体用于携带真正提交给服务器的数据。

GET 请求通常没有请求体，参数一般放在 URL 中；POST、PUT 等请求则经常会携带请求体。

例如提交 JSON 数据：

```http
POST /login HTTP/1.1
Content-Type: application/json

{
  "username": "tom",
  "password": "123456"
}
```

如果是上传图片、文件，请求体里也可以放二进制数据。

## 4. HTTP 响应由什么组成？

服务器收到请求后，会返回 HTTP 响应。一个响应通常包含状态码、响应头和响应体。

### 4.1 状态码

状态码用于告诉客户端请求处理结果。

常见状态码包括：

| 状态码    | 含义             |
| --------- | ---------------- |
| 200       | 请求成功         |
| 201       | 创建成功         |
| 204       | 成功但没有响应体 |
| 301 / 302 | 重定向           |
| 400       | 请求错误         |
| 401       | 未认证           |
| 403       | 无权限           |
| 404       | 资源不存在       |
| 500       | 服务器内部错误   |

比如我们访问一个不存在的页面，服务器通常会返回 404；如果请求成功，则一般返回 200。

### 4.2 响应头

响应头用于描述服务器返回的数据，例如：

```http
Content-Type: text/html
Cache-Control: max-age=3600
Set-Cookie: sessionId=xxx
```text

其中 `Content-Type` 会告诉浏览器响应体是什么类型。比如：

- `text/html` 表示 HTML 页面；
- `application/json` 表示 JSON 数据；
- `image/png` 表示 PNG 图片；
- `application/octet-stream` 表示二进制文件。

### 4.3 响应体

响应体就是服务器真正返回的内容。

它可以是：

- HTML 页面；
- JSON 数据；
- 图片；
- 视频；
- 文件；
- 错误信息。

例如访问一个接口，服务器可能返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "name": "HTTP"
  }
}
```

## 5. 用浏览器开发者工具观察 HTTP

在 Chrome 浏览器中，可以通过开发者工具查看 HTTP 请求。

操作方式是：

1. 打开网页；
2. 右键选择“检查”；
3. 进入 Network 面板；
4. 刷新页面；
5. 查看每一个请求的 Headers、Preview、Response 等信息。

在 Network 面板中，我们可以看到：

- 请求 URL；
- 请求方法；
- 状态码；
- 请求头；
- 响应头；
- 响应体；
- 资源大小；
- 加载耗时。

这对于前端调试、接口排查和性能分析非常重要。

一个页面通常会产生很多请求。浏览器先请求 HTML，拿到 HTML 后再继续请求 CSS、JS、图片等资源。也就是说，打开一个网页，本质上是浏览器不断向服务器请求资源、再把资源组合渲染出来的过程。

## 6. HTTP 运行在哪一层？

从网络分层角度看，HTTP 是 **应用层协议**。

在 OSI 模型中，HTTP 属于第 7 层，即应用层。它关注的是应用程序之间如何表达请求和响应，比如 URL、Header、Body、Status Code 等。

而 HTTP 本身并不直接负责数据如何在网络中可靠传输。真正负责传输的通常是下层协议，比如 TCP 或 QUIC。

可以简单理解为：

- HTTP 负责规定“说什么”；
- TCP/QUIC 负责“怎么送过去”；
- IP 负责“送到哪里”；
- 物理层负责真正的电信号、光信号传输。

在传统 HTTP/1.1 和 HTTP/2 中，HTTP 通常运行在 TCP 之上；而 HTTP/3 则运行在 QUIC 之上，QUIC 又基于 UDP。MDN 也指出，HTTP/3 最明显的变化就是使用 QUIC over UDP，而不是 TCP。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Glossary/HTTP_3?utm_source=chatgpt.com))

## 7. HTTPS 是什么？

HTTPS 可以理解为安全版 HTTP。

HTTP 明文传输，请求和响应内容在网络中可能被窃听或篡改。HTTPS 则在 HTTP 和传输层之间加入 TLS 加密，使通信过程更加安全。

HTTPS 的大致过程是：

1. 客户端和服务器先进行 TLS 握手；
2. 双方协商加密算法和密钥；
3. 后续 HTTP 数据经过加密后再传输；
4. 接收方再解密得到原始内容。

浏览器地址栏中的小锁图标，就表示当前网站使用了 HTTPS。

HTTPS 主要解决三个问题：

- 机密性：别人看不到传输内容；
- 完整性：内容不容易被篡改；
- 身份认证：确认服务器身份，避免访问到伪造网站。

## 8. HTTP/1.0：一次请求一次连接

HTTP/1.0 是较早的 HTTP 版本。

它的主要问题是：每次请求都需要建立一个新的 TCP 连接，请求完成后又关闭连接。

流程大致如下：

```text
建立 TCP 连接
发送 HTTP 请求
服务器返回响应
关闭 TCP 连接
```http

如果一个网页只有一个 HTML 文件，这种方式问题不大。但随着网页越来越复杂，一个页面可能包含很多图片、CSS、JS 文件。每个资源都重新建立连接，就会带来明显的性能浪费。

TCP 建立连接需要三次握手，关闭连接也有成本。如果每个资源都重复建立和关闭连接，网页加载速度就会变慢。

所以 HTTP/1.0 的缺点主要是：

- 连接无法复用；
- 每次请求都要重新建立 TCP；
- 延迟较高；
- 不适合资源数量较多的现代网页。

## 9. HTTP/1.1：持久连接与缓存

HTTP/1.1 对 HTTP/1.0 进行了重要改进，其中最关键的是 **持久连接**。

HTTP/1.1 默认支持连接复用，也就是一个 TCP 连接可以处理多个 HTTP 请求。这样就不需要每次请求都重新建立连接。

它的基本思路是：

```text
建立 TCP 连接
发送第一个请求
返回第一个响应
继续发送第二个请求
返回第二个响应
……
最后关闭连接
```

这大大减少了 TCP 握手带来的开销。

HTTP/1.1 还引入或完善了很多机制，例如：

- Keep-Alive 持久连接；
- 更完善的缓存控制；
- ETag；
- Chunked Transfer Encoding 分块传输；
- Host 请求头。

其中分块传输允许服务器不用等完整响应全部生成后再返回，而是可以一边生成一边发送。比如一个较大的 HTML 页面，服务器可以分成多个块逐步发送给客户端。

不过，HTTP/1.1 仍然存在问题。虽然它可以复用连接，但同一个连接上的请求和响应仍然容易受到顺序影响。如果前面的请求阻塞，后面的请求也可能受到影响，这就是常说的队头阻塞问题。

## 10. HTTP/2：多路复用与二进制分帧

HTTP/2 的目标是进一步提升传输效率。

它保留了 HTTP 的基本语义，比如 URL、请求方法、状态码、Header 等，但改变了底层传输方式。HTTP/2 使用二进制分帧机制，把请求和响应拆分成更小的帧进行传输。

HTTP/2 的核心特性包括：

### 10.1 多路复用

多路复用是 HTTP/2 最重要的改进之一。

在 HTTP/1.1 中，一个 TCP 连接上的请求和响应容易相互等待；而 HTTP/2 可以在同一个 TCP 连接中并发传输多个请求和响应。

这意味着多个资源可以同时通过一个连接传输，不必像 HTTP/1.1 那样受到严格顺序限制。

简单理解：

```text
HTTP/1.1：请求 A -> 响应 A -> 请求 B -> 响应 B

HTTP/2：请求 A、B、C 可以同时在一个连接中传输
```http

这能显著提升复杂网页的加载效率。

### 10.2 Header 压缩

HTTP 请求和响应中会包含大量 Header。很多 Header 在多次请求中是重复的，比如 Cookie、User-Agent、Accept 等。

HTTP/2 使用 HPACK 进行头部压缩，减少重复传输的数据量，从而提高性能。

### 10.3 二进制协议

HTTP/1.1 基于文本格式，可读性较好，但解析效率不如二进制格式。

HTTP/2 改为二进制分帧，机器处理起来更高效，也更适合多路复用。

### 10.4 Server Push

HTTP/2 曾引入 Server Push，即服务器可以在客户端明确请求之前，主动推送可能需要的资源。

例如客户端请求 HTML，服务器可以预测客户端接下来还需要 CSS 和 JS，于是提前推送。

不过在实际使用中，Server Push 的收益和复杂性存在争议，后来很多浏览器和服务端逐渐减少或移除了对它的支持。因此理解 HTTP/2 时，更应该重点关注多路复用、二进制分帧和 Header 压缩。

## 11. HTTP/3：基于 QUIC 的新一代 HTTP

HTTP/3 是 HTTP 的重要版本演进。它不再基于 TCP，而是基于 QUIC。IETF 的 RFC 9114 明确定义了 HTTP/3 是 HTTP 语义在 QUIC 传输协议上的映射。([IETF Datatracker](https://datatracker.ietf.org/doc/html/rfc9114?utm_source=chatgpt.com))

QUIC 基于 UDP，但它并不是简单地“使用 UDP 发送数据”。UDP 本身不保证可靠性、不保证顺序，也没有 TCP 那样的拥塞控制机制。QUIC 在 UDP 之上重新实现了可靠传输、加密、拥塞控制、多路复用等能力。

HTTP/3 的主要优势包括：

### 11.1 减少连接建立延迟

传统 HTTPS 通常需要 TCP 握手和 TLS 握手。QUIC 将传输层和加密能力结合得更紧密，可以减少连接建立所需的往返次数，从而降低延迟。

### 11.2 缓解队头阻塞

HTTP/2 虽然在应用层实现了多路复用，但它仍然运行在 TCP 之上。

TCP 要求字节流按顺序交付。如果某个 TCP 包丢失，后续数据即使已经到达，也要等待丢失的包重传，这会造成传输层队头阻塞。

HTTP/3 基于 QUIC，QUIC 在多个流之间具有更好的独立性。某个流丢包，不会像 TCP 那样严重阻塞其他流。

### 11.3 默认加密

QUIC 默认集成 TLS 1.3，加密成为协议设计的一部分。因此 HTTP/3 天然就是安全传输的一部分。

## 12. HTTP 版本演进总结

可以把 HTTP 的演进理解为不断解决性能问题的过程。

| 版本     | 主要特点                          | 主要问题或改进               |
| -------- | --------------------------------- | ---------------------------- |
| HTTP/1.0 | 一次请求一次连接                  | 连接频繁建立和关闭，开销大   |
| HTTP/1.1 | 持久连接、缓存、分块传输          | 仍存在队头阻塞问题           |
| HTTP/2   | 多路复用、二进制分帧、Header 压缩 | 仍受 TCP 队头阻塞影响        |
| HTTP/3   | 基于 QUIC，运行在 UDP 之上        | 降低延迟，缓解传输层队头阻塞 |

HTTP 的本质没有变，依然是请求和响应；变的是它底层传输数据的方式越来越高效。

## 13. 如何自己启动一个 HTTP Web Server？

学习 HTTP 最好的方式之一，就是自己启动一个简单的 Web Server。

例如使用 Node.js 的 `http-server` 工具：

```bash
npm install -g http-server
```

然后在某个项目目录下创建 `index.html`：

```html
<!DOCTYPE html>
<html>
  <head>
    <meta charset="UTF-8" />
    <title>My First Website</title>
  </head>
  <body>
    <h1>Hello HTTP</h1>
  </body>
</html>
```text

进入该目录后执行：

```bash
http-server
```

默认情况下，它可能会启动在：

```text
http://localhost:8080
```ts

然后在浏览器中访问这个地址，就能看到自己写的 HTML 页面。

也可以在浏览器控制台中使用 `fetch` 发起请求：

```javascript
fetch("http://localhost:8080")
  .then((res) => res.text())
  .then((data) => console.log(data));
```

这段代码会向本地服务器发送 HTTP 请求，并把服务器返回的 HTML 内容打印出来。

通过这种方式，我们就能更直观地理解：

- 浏览器如何发请求；
- 服务器如何返回响应；
- 请求头和响应头长什么样；
- HTML、CSS、JS、图片是如何被加载的。

## 14. 总结

HTTP 是 Web 世界的基础协议。它采用客户端—服务器模型，通过请求和响应完成资源传输。

一个 HTTP 请求通常包含 URL、请求方法、请求头和请求体；一个 HTTP 响应通常包含状态码、响应头和响应体。浏览器打开网页，本质上就是不断发送 HTTP 请求、接收 HTTP 响应、解析资源并渲染页面的过程。

HTTP 的发展经历了多个阶段：

HTTP/1.0 简单直接，但每次请求都要建立连接，性能较差；HTTP/1.1 引入持久连接和缓存机制，提升了效率；HTTP/2 通过多路复用、二进制分帧和 Header 压缩进一步优化性能；HTTP/3 则基于 QUIC，把传输层从 TCP 转向 UDP 之上的 QUIC，以降低延迟并缓解队头阻塞问题。

理解 HTTP，不只是理解一个协议，更是在理解整个 Web 应用如何运转。对于前端、后端、网络编程和系统设计来说，HTTP 都是必须掌握的基础知识。
