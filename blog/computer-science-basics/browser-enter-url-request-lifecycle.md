# 当你在浏览器输入 google.com 并按下 Enter，背后到底发生了什么？

很多人每天都会在浏览器地址栏输入一个网址，比如 `google.com`，然后按下 Enter。页面很快打开，看起来只是一个简单动作。但在这短短几百毫秒到几秒之间，浏览器、操作系统、DNS、路由器、TCP、TLS、HTTP 以及服务器之间已经完成了一整套复杂的协作。

本文将从网络和软件工程的角度，梳理一次访问 `google.com` 的完整过程。为了便于理解，假设这是一个全新的浏览器和全新的设备，用户此前从未访问过 Google，也没有任何浏览历史、DNS 缓存或 Cookie。

---

## 一、输入阶段：浏览器如何理解你输入的内容

当用户开始在地址栏输入 `google.com` 时，浏览器首先会尝试判断用户输入的内容是什么。

如果用户只输入了一个字母，比如 `g`，浏览器可能会查询本地浏览历史、书签、缓存索引，甚至向默认搜索引擎发送联想请求，用来展示自动补全结果。但在我们的假设中，这是一台全新的机器，浏览器没有任何历史记录，因此不会匹配到已有页面。

当用户完整输入 `google.com` 并按下 Enter 后，浏览器会进一步判断：这到底是一个搜索关键词，还是一个 URL？

如果浏览器认为它是搜索词，就会把它提交给默认搜索引擎。如果浏览器判断它是一个网址，就会开始访问这个网站。这里我们讨论的是后者，也就是浏览器确认用户想访问 `google.com`。

---

## 二、确定协议：HTTP 还是 HTTPS？

用户只输入了 `google.com`，并没有输入：

```text
http://google.com
```text

也没有输入：

```text
https://google.com
```

因此，浏览器需要判断应该使用哪种协议访问该网站。

早期浏览器通常会默认尝试 HTTP，也就是未加密的 80 端口。但这种方式存在明显安全风险，容易受到中间人攻击，例如 SSL Stripping 攻击。现在很多浏览器会优先尝试 HTTPS，或者通过 HSTS 机制判断某个网站是否必须使用 HTTPS。

HSTS 的全称是 HTTP Strict Transport Security，即 HTTP 严格传输安全。浏览器会维护一份 HSTS 列表，里面记录了一些只允许通过 HTTPS 访问的网站。如果 `google.com` 在这份列表中，浏览器就会直接使用 HTTPS，也就是连接 443 端口。

因此，在这个例子中，浏览器最终会选择：

```text
协议：https
端口：443
```text

---

## 三、DNS 查询：把域名转换成 IP 地址

浏览器知道要访问 `google.com`，也知道要使用 HTTPS 的 443 端口。但仅有域名还不够，真正的网络通信需要 IP 地址。

所以，浏览器需要进行 DNS 查询，把：

```text
google.com
```

解析成类似下面这样的 IP 地址：

```text
4.1.2.3
```text

这里的 IP 只是示例，不代表 Google 的真实地址。

DNS 查询并不是直接向外部服务器请求，它会经历多层检查。

首先，浏览器会查看自己的 DNS 缓存。如果之前访问过 `google.com`，浏览器可能已经保存了对应的 IP 地址。但在我们的假设中，这是第一次访问，所以浏览器缓存中没有记录。

接着，浏览器会询问操作系统。操作系统可能会检查本地 DNS 缓存，也可能会查看 hosts 文件。hosts 文件可以手动指定某个域名对应哪个 IP 地址，例如：

```text
127.0.0.1 google.com
```

如果 hosts 文件中没有相关记录，系统才会继续向配置好的 DNS 服务器发起查询。

一般情况下，DNS 服务器由路由器或 ISP 自动分配，也可以手动设置为公共 DNS，例如：

```text
1.1.1.1
8.8.8.8
```text

传统 DNS 通常使用 UDP 协议，端口是 53。它的缺点是默认不加密，网络中的某些节点，比如 ISP，可能知道用户正在查询哪些域名。为了解决这个问题，现在也出现了 DNS over HTTPS 和 DNS over TLS 等方案，用加密方式完成 DNS 查询。

在普通 DNS 查询中，客户端会向 DNS 服务器发送一个 UDP 数据报，请求解析 `google.com`。DNS 服务器返回对应的 IP 地址后，浏览器才知道真正要连接的服务器是谁。

---

## 四、局域网转发：为什么需要 MAC 地址和网关？

知道目标 IP 地址以后，客户端还不能直接把数据发到互联网上。因为在局域网中，数据帧的传输还需要 MAC 地址。

假设当前设备的局域网 IP 是：

```text
10.0.0.2
```

路由器，也就是默认网关的 IP 是：

```text
10.0.0.1
```text

客户端要访问的 DNS 服务器是：

```text
1.1.1.1
```

客户端会判断 `1.1.1.1` 是否在自己的局域网内。显然不在。因此，它不会尝试直接寻找 `1.1.1.1` 的 MAC 地址，而是把数据交给默认网关，也就是路由器。

如果客户端不知道路由器的 MAC 地址，就会通过 ARP 协议查询。获得路由器的 MAC 地址后，客户端会把数据帧发给路由器。

注意，这里的二层目标 MAC 地址是路由器的 MAC 地址，但三层目标 IP 地址仍然是最终目标，例如 `1.1.1.1`。路由器收到数据后，会继续把它转发到互联网上。

---

## 五、NAT：内网地址如何访问公网？

局域网 IP 地址，例如 `10.0.0.2`，是私有地址，不能直接在公网中路由。因此，路由器需要进行 NAT，也就是网络地址转换。

假设路由器的公网 IP 是：

```text
44.1.2.4
```text

客户端向 DNS 服务器发送请求时，源地址原本是：

```text
10.0.0.2:3333
```

路由器会把它转换成：

```text
44.1.2.4:3333
```text

同时，路由器会在 NAT 表中记录一条映射关系：

```text
44.1.2.4:3333  <->  10.0.0.2:3333
```

这样，当 DNS 服务器返回响应时，它只会把响应发给路由器的公网 IP。路由器收到响应后，再根据 NAT 表把数据转发回局域网中的客户端。

通过这个过程，客户端最终拿到了 `google.com` 的 IP 地址。

---

## 六、建立 TCP 连接：三次握手

拿到 Google 服务器的 IP 地址后，浏览器需要建立 TCP 连接。

因为我们访问的是 HTTPS，所以目标端口是 443。客户端会随机选择一个本地端口，例如：

```text
10.0.0.2:2222
```text

目标则是：

```text
4.1.2.3:443
```

TCP 是面向连接的协议。在真正发送 HTTP 请求之前，客户端和服务器之间需要完成三次握手：

```text
客户端 -> 服务器：SYN
服务器 -> 客户端：SYN + ACK
客户端 -> 服务器：ACK
```text

三次握手完成后，客户端和服务器之间就建立了一条可靠的 TCP 连接。

这个过程中，数据仍然会经过路由器 NAT。路由器会记录新的 NAT 映射，例如：

```text
44.1.2.4:2222  <->  10.0.0.2:2222
```

此时，浏览器和 Google 服务器之间已经建立了 TCP 连接，但还没有真正发送网页请求。

---

## 七、TLS 握手：建立加密通道

因为我们访问的是 HTTPS，所以 TCP 连接建立之后，还需要进行 TLS 握手。

TLS 的作用是建立一个安全的加密通道，防止通信内容被窃听或篡改。

以 TLS 1.3 为例，客户端会先发送 Client Hello，其中可能包含：

```text
支持的 TLS 版本
支持的加密套件
客户端随机数
密钥交换参数
SNI
ALPN
```http

SNI 的全称是 Server Name Indication，也就是服务器名称指示。它的作用是告诉服务器：虽然我连接的是某个 IP 地址，但我真正要访问的域名是 `google.com`。

这是因为同一个 IP 地址可能承载多个网站。如果没有 SNI，服务器可能不知道应该返回哪个网站的证书。

ALPN 的全称是 Application-Layer Protocol Negotiation，也就是应用层协议协商。通过 ALPN，浏览器可以告诉服务器自己支持哪些应用层协议，例如：

```text
HTTP/1.1
HTTP/2
HTTP/3
```

服务器收到 Client Hello 后，会选择合适的 TLS 版本、加密套件和应用层协议，并返回 Server Hello，同时发送证书。客户端会验证证书是否合法，例如证书是否过期、域名是否匹配、是否由可信 CA 签发等。

验证通过后，双方通过密钥交换算法生成共享密钥。之后的数据就可以使用对称加密进行加密和解密。

到这一步，浏览器和服务器之间才真正拥有了一条安全的通信通道。

---

## 八、发送 HTTP 请求

TLS 通道建立完成后，浏览器终于可以发送 HTTP 请求了。

如果访问的是首页，浏览器通常会发送一个 GET 请求：

```http
GET / HTTP/2
Host: google.com
User-Agent: ...
Accept: text/html
```text

如果之前访问过该网站，浏览器还可能带上 Cookie。但在我们的假设中，这是第一次访问，因此不会携带已有 Cookie。

如果客户端和服务器协商使用的是 HTTP/2，那么请求会被组织成 HTTP/2 的二进制帧，并通过同一条 TCP 连接中的 stream 发送。HTTP/2 的一个重要特点是多路复用，也就是多个请求可以复用同一条 TCP 连接并行传输。

浏览器将 HTTP 请求交给 TLS 层加密，再通过 TCP 连接发送出去。服务器收到数据后，先解密，再解析 HTTP 请求。

---

## 九、服务器处理请求并返回响应

Google 的服务器并不是一台简单的机器。真实环境中，请求可能会先经过负载均衡器、边缘节点、反向代理、缓存系统，再转发到后端服务。

如果是四层负载均衡，它主要根据 IP 和端口转发流量。如果是七层负载均衡，它可能会终止 TLS，解析 HTTP 请求，再根据路径、Header、Cookie 等信息决定把请求转发到哪个后端服务。

服务器最终会生成一个 HTTP 响应，例如：

```http
HTTP/2 200 OK
Content-Type: text/html
Set-Cookie: ...
```

响应体中包含 HTML 内容。服务器可能还会通过 `Set-Cookie` 让浏览器保存一些 Cookie，用于会话识别、个性化或统计分析。

服务器返回的数据同样会经过 HTTP/2 编码、TLS 加密、TCP 传输、路由器 NAT 转发，最终回到客户端浏览器。

---

## 十、浏览器解析 HTML 并继续加载资源

浏览器收到响应后，会先通过 TLS 解密数据，然后解析 HTTP 响应头。

如果响应头中的 `Content-Type` 是：

```http
Content-Type: text/html
```tsx

浏览器就会把响应体当作 HTML 解析。

在解析 HTML 的过程中，浏览器可能会发现页面还需要加载其他资源，例如：

```html
<link rel="stylesheet" href="style.css" />
<script src="main.js"></script>
<img src="logo.png" />
```

于是，浏览器会继续发起新的请求来获取 CSS、JavaScript、图片等资源。

如果使用 HTTP/2，这些资源请求可以通过同一条 TCP 连接上的多个 stream 并行发送，而不需要像 HTTP/1.1 那样建立多条 TCP 连接。

服务器返回这些资源后，浏览器会解析 CSS、执行 JavaScript、解码图片，并逐步构建页面：

```text
HTML -> DOM
CSS -> CSSOM
DOM + CSSOM -> Render Tree
Layout -> Paint -> Composite
```http

最终，用户就看到了 Google 首页。

---

## 十一、一些可能的分支情况

上面的流程是一个相对标准的 HTTPS 访问流程。但真实浏览器和真实网络环境中，还可能出现很多分支。

比如，如果浏览器启用了 DNS over HTTPS，DNS 查询就不会通过传统 UDP 53 端口完成，而是会通过 HTTPS 发送给指定的 DoH 服务。

如果用户配置了代理，浏览器连接的目标可能不是 Google 服务器，而是代理服务器。代理再负责向 Google 发起请求。

如果使用的是 HTTP/1.1，浏览器可能会建立多条 TCP 连接，以便并发加载多个资源。

如果使用的是 HTTP/3，请求可能不再基于 TCP，而是基于 QUIC。QUIC 运行在 UDP 之上，可以减少连接建立和加密握手的延迟。

如果服务器启用了 HTTP/2 Server Push，它甚至可以在浏览器请求 CSS 或 JavaScript 之前，主动把这些资源推送给浏览器。不过这种机制在实际使用中存在争议，现在已经不再是主流优化方向。

---

## 十二、总结

当用户输入 `google.com` 并按下 Enter，看似只是一次简单访问，背后却经历了大量步骤：

```text
浏览器解析输入
判断 URL 或搜索词
确定 HTTP/HTTPS 协议
查询 HSTS
进行 DNS 解析
通过 ARP 找到网关 MAC 地址
经过 NAT 访问公网
建立 TCP 连接
完成 TLS 握手
协商 HTTP 协议版本
发送 HTTP 请求
服务器处理请求
返回 HTML 响应
浏览器解析页面
继续加载 CSS、JS、图片等资源
最终渲染页面
```

这整个过程体现了现代互联网协议栈的复杂性。浏览器、操作系统、路由器、DNS、TCP、TLS、HTTP 和服务器共同协作，才让用户能够在极短时间内看到一个网页。

所以，下次当你在浏览器里输入一个网址并按下 Enter 时，不妨想一想：在页面打开之前，网络世界已经完成了一场精密而复杂的接力。
