# TCP 三次握手：别只会背 SYN、SYN-ACK、ACK

很多人提到 TCP 三次握手，第一反应就是背流程：SYN、SYN-ACK、ACK。

但如果面试时只会说这三个词，基本等于没有真正答到点上。因为面试官真正想听的，不是你记不记得流程，而是你是否理解：为什么一定要三次？每一次到底在确认什么？少一次行不行？

这篇文章就用最容易理解的方式，把 TCP 三次握手讲清楚。

## 一、TCP 为什么需要三次握手？

TCP 是一种可靠连接。

所谓可靠连接，并不是说网络本身一定可靠，而是 TCP 会在不可靠的网络环境中，通过一系列机制尽量保证通信可靠。比如确认机制、重传机制、滑动窗口、流量控制、拥塞控制等。

但在真正传输数据之前，客户端和服务端首先要确认一件事：

双方是否都具备正常通信的能力。

换句话说，客户端要确认自己能发、服务端能收；服务端也要确认自己能发、客户端能收。只有这些状态都确认完成之后，TCP 连接才算真正建立。

这个确认过程，就是三次握手。

三次握手的本质，并不是简单地打三次招呼，而是在同步双方的通信状态。

## 二、第一次握手：客户端发送 SYN

第一次握手时，客户端会向服务端发送一个 SYN 包。

你可以把它理解成客户端在说：

“你好，我想和你建立连接。”

但第一次握手并不只是打招呼。客户端还会带上一个非常关键的信息：随机序列号，也就是 Sequence Number，简称 SEQ。

这个序列号后面会用于数据确认和重传。

也就是说，第一次握手的含义是：

客户端告诉服务端：我想建立连接，并且我后面发送的数据会从这个序列号开始。

此时，客户端从 CLOSED 状态进入 SYN-SENT 状态。

## 三、第二次握手：服务端返回 SYN + ACK

服务端收到客户端的 SYN 后，会返回一个 SYN + ACK。

这个响应其实包含两层意思。

第一层是 ACK：
“你的请求我收到了。”

第二层是 SYN：
“我也准备好了，我也想和你建立连接。”

在这一步中，服务端也会生成自己的 SEQ，同时 ACK 会等于客户端的 SEQ + 1。

这个 ACK 的意思是：

“客户端，你刚才发来的 SYN 我已经收到了，我期待你下一个数据从 SEQ + 1 开始。”

到这里，前两次握手已经完成了两个方向的确认：

客户端能发，服务端能收；服务端也能发出响应。

但这还不够。

因为服务端虽然发出了响应，但它并不知道客户端到底有没有收到自己的响应。

所以还需要第三次握手。

## 四、第三次握手：客户端返回 ACK

第三次握手时，客户端收到服务端的 SYN + ACK 后，会再发送一个 ACK 给服务端。

这一步非常关键。

它代表客户端在告诉服务端：

“你刚才发给我的消息，我也收到了。”

到这里，双方才真正确认了四件事：

客户端能发，服务端能收；
服务端能发，客户端能收。

此时，客户端和服务端都进入 ESTABLISHED 状态，TCP 连接正式建立完成。

## 五、为什么不能只握手两次？

这是 TCP 三次握手里最经典的面试题。

如果只有两次握手，看起来似乎也能建立连接：

客户端发送 SYN；
服务端返回 SYN + ACK。

但问题在于，服务端并不知道客户端是否真的收到了自己的响应。

举个例子。

假设客户端曾经发送过一个 SYN 请求，但由于网络延迟，这个 SYN 在网络里滞留了很久。客户端等不到响应，就放弃了这次连接。

过了一段时间，这个旧的 SYN 请求终于到达服务端。

如果 TCP 只需要两次握手，那么服务端收到 SYN 后，返回 SYN + ACK，就会直接认为连接已经建立成功。

但实际上，客户端早就不想建立这个连接了。

结果就是，服务端会维护一个根本不存在的连接，并等待客户端继续发送数据。客户端不会再发送任何数据，服务端资源却被白白占用。

如果这种历史延迟请求大量出现，就可能造成很多无效连接，浪费服务端资源。

所以第三次握手的作用，就是让客户端再确认一次：

“我确实收到了服务端的响应，并且我现在仍然要建立这个连接。”

这一步可以有效避免历史延迟请求导致错误连接建立。

## 六、三次握手中的状态变化

理解三次握手时，也要顺便记住 TCP 状态的变化。

客户端一开始是 CLOSED 状态。
当客户端发送 SYN 后，进入 SYN-SENT 状态。
服务端收到 SYN 后，进入 SYN-RCVD 状态。
客户端收到服务端的 SYN + ACK 后，发送 ACK。
最后双方都进入 ESTABLISHED 状态。

ESTABLISHED 就表示 TCP 连接正式建立，可以开始传输数据了。

## 七、三次握手到底在确认什么？

总结一下，TCP 三次握手并不是为了机械地执行三步流程，而是在确认双方的发送和接收能力。

第一次握手确认：

客户端能发，服务端能收。

第二次握手确认：

服务端收到了客户端的请求，并且服务端也能发。

第三次握手确认：

客户端收到了服务端的响应，服务端能发、客户端能收这件事也成立。

最终确认的就是四件事：

客户端能发；
客户端能收；
服务端能发；
服务端能收。

只有这四件事都被确认，TCP 才会认为连接是可靠建立的。

## 八、为什么面试爱问 TCP 三次握手？

因为 TCP 三次握手不是一个孤立知识点。

它背后体现的是网络通信中的一个核心问题：

在不可靠的网络环境下，双方如何安全、准确地建立连接。

TCP 后面的可靠传输、确认应答、超时重传、滑动窗口、流量控制、拥塞控制，都是建立在这个连接基础之上的。

所以面试官问三次握手，并不是想听你背 SYN、SYN-ACK、ACK，而是想看你是否真正理解 TCP 的可靠性设计。

## 九、最后总结

TCP 三次握手可以简单记成 SYN、SYN-ACK、ACK，但不能只停留在这三个词上。

它真正解决的问题是：

在网络不可靠的情况下，客户端和服务端如何确认双方都具备正常通信能力，并避免历史延迟请求造成错误连接。

第一次握手，客户端告诉服务端自己要建立连接。
第二次握手，服务端确认收到请求，并告诉客户端自己也准备好了。
第三次握手，客户端确认收到服务端响应，连接正式建立。

所以，三次握手的核心不是“握了三次”，而是双方通过三次交互，完成了发送能力、接收能力和初始序列号的同步确认。

这才是 TCP 三次握手真正要理解的地方。
