# 浏览器同源策略详解：它到底限制了什么？

在现代 Web 开发中，**同源策略**是一个非常基础但又非常重要的安全机制。很多人在学习前端安全、跨域请求、iframe、Cookie、CORS 时，都会遇到这个概念。

同源策略看起来有点抽象，但它解决的问题其实很现实：

**浏览器如何防止一个网站随便读取另一个网站的数据？**

比如你同时打开了一个普通网页和你的网上银行页面。你肯定不希望普通网页里的 JavaScript 能够读取银行页面的 DOM、Cookie 或用户输入内容。否则，只要你打开了恶意网站，你的账号、密码、会话信息都可能被窃取。

同源策略就是浏览器用来防止这类问题的重要安全边界。

---

## 一、什么是“源”？

在理解同源策略之前，必须先理解什么是“源”。

在浏览器中，一个 URL 的“源”由三个部分决定：

```text
协议 + 域名 + 端口
```text

也就是说，两个 URL 只有在以下三个部分完全相同时，才算是同源：

协议相同；

主机名相同；

端口相同。

例如：

```text
https://mydomain.com/page1
https://mydomain.com/page2
```

这两个 URL 是同源的。

因为它们的协议都是 `https`，域名都是 `mydomain.com`，端口也相同。路径 `/page1` 和 `/page2` 并不影响源的判断。

再看下面这个例子：

```text
https://mydomain.com
https://example.com
```text

这两个 URL 不同源。

虽然协议相同，端口也相同，但域名不同，一个是 `mydomain.com`，另一个是 `example.com`。

再比如：

```text
http://mydomain.com
https://mydomain.com
```

这两个也不同源。

因为协议不同，一个是 `http`，另一个是 `https`。

还有：

```text
https://mydomain.com:443
https://mydomain.com:3000
```text

这两个也不同源。

因为端口不同。

所以，同源判断只看三个东西：

```text
协议、域名、端口
```

路径、查询参数、hash 都不影响是否同源。

---

## 二、同源策略要解决什么问题？

现代浏览器允许用户同时打开很多页面。你可以同时打开：

一个绘图网站；

一个社交网站；

一个文档页面；

一个银行页面；

一个后台管理系统。

这些页面可能来自完全不同的源。

如果浏览器没有同源策略，那么一个恶意网站中的 JavaScript 就可能访问另一个网站的页面内容。

比如你打开了一个恶意网页，同时又登录着网上银行。如果恶意网页里的脚本可以读取银行页面的 DOM，那么它就可能拿到你的账户信息、交易记录，甚至读取你输入的用户名和密码。

这显然是不可接受的。

所以，同源策略的核心目的就是：

**限制一个源中的脚本访问另一个源中的敏感数据。**

它不是为了限制所有资源，而主要是限制脚本能做什么。

---

## 三、同源策略主要限制的是脚本

很多人容易误解同源策略，以为它会阻止所有跨源资源加载。

其实不是。

同源策略主要关注的是：

```text
一个源中的 JavaScript，能不能读取或操作另一个源中的内容。
```tsx

也就是说，它重点限制的是脚本行为，而不是简单地禁止跨源资源加载。

例如，一个网站通常可以加载跨源图片：

```html
<img src="https://example.com/image.png" />
```

也可以加载跨源 CSS：

```html
<link rel="stylesheet" href="https://example.com/style.css" />
```tsx

也可以加载跨源脚本：

```html
<script src="https://cdn.example.com/lib.js"></script>
```

但是，脚本能不能读取另一个源的 DOM、Cookie、响应内容，这就是同源策略关心的问题。

一句话总结：

**同源策略不是禁止跨源资源存在，而是限制跨源读取和跨源操作。**

---

## 四、iframe 中的跨源限制

iframe 是理解同源策略的一个经典场景。

假设一个页面是：

```text
https://draw.io
```tsx

页面中嵌入了一个 iframe：

```html
<iframe src="https://email-marketing.com/widget"></iframe>
```

这个 iframe 里可能是一个邮件订阅表单，用户可以输入邮箱来订阅 newsletter。

从页面结构上看，iframe 被嵌入在当前页面里，好像它是页面的一部分。但从浏览器安全模型来看，iframe 其实是另一个独立文档。如果 iframe 的地址和父页面不同源，那么父页面里的 JavaScript 就不能随便读取 iframe 里面的内容。

例如，父页面里的脚本不能随便这样做：

```js
const iframeDocument = iframe.contentWindow.document;
console.log(iframeDocument.body.innerHTML);
```tsx

如果 iframe 是跨源的，浏览器会阻止这类访问。

原因很简单。

假设一个恶意网站嵌入了你的银行网站：

```html
<iframe src="https://bank.com"></iframe>
```

如果恶意网站的脚本可以读取 iframe 内容，那么用户在银行页面中输入的账号和密码，就可能被恶意脚本读取。

所以，跨源 iframe 的 DOM 访问必须受到严格限制。

这就是同源策略非常重要的一个应用场景。

---

## 五、同源页面之间可以互相访问吗？

可以，但有条件。

如果两个页面是同源的，并且一个页面持有另一个页面的引用，比如通过 `window.open` 打开了另一个页面，那么它们之间是可以进行一定程度的访问和操作的。

例如：

```js
const newWindow = window.open("https://mydomain.com/page2");
```ts

如果当前页面和新打开的页面同源，那么当前页面可以访问新页面的 DOM。

但是，如果打开的是不同源页面：

```js
const newWindow = window.open("https://example.com");
```

那么访问就会受到限制。

所以并不是说浏览器完全禁止页面之间互相访问，而是说：

**只有同源页面之间，浏览器才允许更自由的访问。**

跨源页面之间，访问会被严格限制。

---

## 六、脚本文件来自 CDN，它的源算谁的？

这是一个非常容易误解的问题。

假设当前页面是：

```text
https://draw.io
```tsx

然后页面加载了一个来自其他域名的脚本：

```html
<script src="https://cdn.stripe.com/library.js"></script>
```

很多人会以为，这个脚本来自 `cdn.stripe.com`，所以它的源就是 `cdn.stripe.com`。

但实际上，从同源策略的角度看：

**脚本的执行权限属于它被嵌入的文档，而不是它下载来源的域名。**

也就是说，这个脚本虽然是从 `cdn.stripe.com` 下载的，但它运行在 `https://draw.io` 这个页面中，所以它拥有当前页面的权限。

它可以访问当前页面的 DOM，可以修改当前页面内容，可以读取当前页面中同源可访问的数据。

这也是为什么引入第三方脚本要非常谨慎。

因为一旦你在页面中引入某个外部脚本，它基本就可以在你的页面上下文中执行代码。

例如：

```html
<script src="https://third-party.com/tracker.js"></script>
```text

这个脚本并不是以 `third-party.com` 的权限运行，而是在你的页面里运行。

所以它可以操作你的页面 DOM。

这也是为什么第三方脚本供应链安全非常重要。

---

## 七、同源策略允许跨源“写”，但限制跨源“读”

同源策略并不是完全禁止跨源请求。

通常来说，浏览器允许某些跨源“写入”行为，例如提交表单、发送一些简单请求、加载图片、加载脚本等。

但是，它会限制跨源“读取”。

也就是说，一个网站可以尝试向另一个源发送请求，但它不能随便读取另一个源返回的数据。

举个例子：

```js
fetch("https://api.example.com/data");
```

如果这是一个跨源请求，浏览器并不是一定完全不发送请求。请求可能会发出去，但是浏览器会根据 CORS 等机制判断前端 JavaScript 是否有权限读取响应结果。

同源策略的核心限制可以理解为：

```text
允许嵌入一些跨源资源；
允许发出某些跨源请求；
但不允许随便读取跨源响应内容；
也不允许随便操作跨源 DOM。
```text

这也是为什么我们经常会遇到“跨域请求被浏览器拦截”的问题。

严格来说，很多时候不是请求没有发出去，而是浏览器不允许你的 JavaScript 读取响应。

## 八、同源策略和 CORS 的关系

学习同源策略时，经常会遇到另一个概念：CORS。

CORS 的全称是 Cross-Origin Resource Sharing，中文通常叫“跨源资源共享”。

同源策略是浏览器默认的安全限制。

CORS 则是一种让服务器明确告诉浏览器：

```text
这个跨源请求是被允许的。
```

比如服务器返回响应头：

```http
Access-Control-Allow-Origin: https://example.com
```text

这表示服务器允许 `https://example.com` 这个源读取响应。

所以可以简单理解为：

**同源策略是默认限制，CORS 是服务器用来放行跨源读取的机制。**

如果没有 CORS，浏览器会按照同源策略限制跨源读取。

如果服务器正确配置了 CORS，浏览器才会允许前端 JavaScript 读取跨源响应。

---

## 九、为什么说同源策略有时太严格，有时又不够严格？

同源策略是浏览器安全的基础，但它并不是所有安全问题的完整解决方案。

有时它会显得太严格。

比如前端应用调用自己的后端 API，但前端和后端部署在不同域名或端口下：

```text
前端：http://localhost:3000
后端：http://localhost:8080
```

虽然它们都是你自己的项目，但因为端口不同，所以浏览器认为它们不同源。这时候就会触发跨域限制，需要配置 CORS。

但有时它又不够严格。

比如页面引入第三方脚本：

```html
<script src="https://third-party.com/script.js"></script>
```text

这个脚本虽然来自第三方，但一旦被引入页面，它就可以在当前页面上下文中运行，拥有相当高的权限。

所以，同源策略并不是万能安全机制。它主要解决的是跨源读取和跨源 DOM 访问问题，但并不能自动保证你引入的第三方脚本是安全的。

---

## 十、同源策略到底限制了什么？

可以把同源策略的限制总结为几类。

### 1. 限制跨源 DOM 访问

一个源中的脚本不能随便读取或修改另一个源页面的 DOM。

例如，父页面不能随便读取跨源 iframe 的内容。

### 2. 限制跨源 Cookie 访问

一个源的脚本不能直接读取另一个源的 Cookie。

比如 `draw.io` 的脚本不能读取 `bank.com` 的 Cookie。

### 3. 限制跨源响应读取

一个源中的脚本不能随便读取另一个源接口返回的数据。

除非目标服务器通过 CORS 明确允许。

### 4. 不完全禁止跨源资源加载

图片、CSS、脚本、iframe 等资源在很多情况下可以跨源加载。

但是“能加载”不等于“能读取里面的内容”。

---

## 十一、开发中如何理解同源策略？

在实际开发中，可以这样理解：

只要你的 JavaScript 想读取另一个源的数据，就要考虑同源策略。

比如：

跨域调用 API；

读取 iframe 内容；

操作新打开窗口的 DOM；

读取其他域名的 Cookie；

获取跨源请求的响应内容。

这些行为都可能受到同源策略限制。

但如果只是加载图片、加载 CSS、加载脚本，情况就不一样。浏览器通常允许跨源加载这些资源，但依然会对读取能力做限制。

---

## 十二、总结

同源策略是浏览器最重要的安全机制之一。

它定义了一个基本边界：

```text
一个源中的脚本，不能随便读取或操作另一个源中的敏感内容。
```

其中，“源”由协议、域名和端口共同决定。只有这三者完全相同，才算同源。

同源策略主要限制的是脚本行为，尤其是跨源读取、跨源 DOM 操作、跨源 Cookie 访问等。

它并不完全禁止跨源资源加载。图片、CSS、脚本、iframe 等资源都可能被跨源加载，但加载不代表可以自由读取和操作。

在现代前端开发中，同源策略和 CORS 经常一起出现。可以简单理解为：

**同源策略负责默认限制，CORS 负责在服务器允许的情况下放行跨源读取。**

掌握同源策略之后，再去理解跨域请求、CORS、iframe 安全、Cookie 安全、第三方脚本风险，就会清晰很多。

一句话总结：

**同源策略保护的是浏览器中的数据边界，它防止一个网站的脚本随便读取另一个网站的内容。**
