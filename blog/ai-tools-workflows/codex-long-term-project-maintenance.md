# 我是如何用 Codex 维护长期项目的：从项目管理、文件记忆到局部 Skill

很多人使用 Codex，可能还停留在“问一句、答一句”的阶段。但如果你真的想用它维护一个长期项目，不管是写代码、做内容、管理数据，还是处理创业任务，仅仅靠聊天是不够的。

我自己在日常使用中，会把 Codex 当成一个可以长期协作的项目助手。它不只是帮我回答问题，而是会基于项目文件、工作流和局部 Skill，持续参与我的创作和复盘。

这篇文章就分享一下，我是如何在 Codex 里面管理长期项目的。

## 一、Projects 和 Chats 的区别

在 Codex 左侧栏里，我们可以看到两种主要的话题类型：Projects 和 Chats。

Chats 更像我们平时使用 ChatGPT 的方式，适合处理一些比较轻量、临时、简短的问题。比如我只是想让它帮我想几个标题、出一个简单方案，或者处理一个不需要长期留档的小任务，就可以直接在 Chats 里对话。

当然，如果聊着聊着发现某些内容很重要，也可以让它写入本地文件。只是这种对话没有绑定到某一个指定工作区里，它更适合临时任务。

Projects 则不一样。

对于开发者来说，项目是一个非常熟悉的概念。每一个应用、每一个代码库，都会有自己的工作区。这个工作区里面包含所有代码、配置、文档和相关文件。

在 Codex 里，项目也是类似的。它会围绕一个具体目录工作，能够读取这个目录中的文件，并基于项目内容进行修改、补充和管理。

对于开发任务来说，代码就是 Agent 的记忆。每一次新开对话，AI 并不知道你之前聊过什么，但它可以通过读取代码库，了解当前项目有什么文件、做过哪些设计、接下来应该改哪里。

这对非代码任务同样成立。

如果我们做的是内容管理、数据复盘、文档写作或者项目运营，那么项目目录里的文档、表格、素材、流程文件，也可以成为 AI 的长期记忆。

## 二、用项目目录管理长期内容资产

我自己的一个例子，是用 Codex 管理小红书相关的数据和内容流程。

我会创建一个专门的项目，比如叫 red note。这个项目里面存放我以前的视频数据、口播稿、内容卡片、创作流程、数据复盘结果等内容。

创建项目时，可以从空项目开始，也可以选择一个已有目录。我一般会先在本地创建好目录，然后在 Codex 里选择这个目录作为项目工作区。

项目创建完成后，可以通过右侧的 Files 面板查看当前项目里的文件。

比如在我的项目里，会有一些用于存储口播稿的小卡片，也会有一些历史数据文件。这些数据可能来自创作中心，也可能是我让 AI 通过自动化流程拉取、整理和复盘的结果。

这样做的好处是，项目不是散落在一次次聊天里，而是沉淀在文件系统里。

聊天会断，记忆会丢，但文件一直在。

## 三、用 AGENTS.md 作为项目入口文件

虽然 Codex 可以读取项目文件，但每次进入新对话时，它并不会天然知道这个项目到底是干什么的。

所以我会在项目里初始化一个 `AGENTS.md` 文件。

这个文件可以理解成项目的入口说明，也可以理解成 Agent 的项目使用手册。很多 Agent 都会遵循这种规范：进入项目后，优先读取这个文件，从而快速理解项目背景、目录结构和工作规则。

如果项目里还没有 `AGENTS.md`，可以直接让 AI 做一件事：

```text
请你扫描我的代码仓库，写一个 AGENTS.md。
```

对于我的小红书内容项目来说，`AGENTS.md` 里会说明这个项目的定位：

这个项目用于管理我的小红书 AI 工具实操内容流程，包括选题、拍摄、数据复盘和内容沉淀。

同时，它还会列出一些重要文件和目录，让 Agent 知道哪些文件对应什么流程，什么时候应该读取哪些参考资料。

这个文件不需要写得特别复杂。它的作用不是替代所有文档，而是给 Agent 一个最基础的项目认知。

之后只要我在这个项目里对话，它通常都会先读取这个入口文件，对当前项目形成基本理解。

## 四、不要把所有 Skill 都放到全局

除了项目文件，我还会用 Skill 来处理一些固定流程。

很多人会把 Skill 装在全局环境里。这样虽然方便，但也有一个问题：当全局 Skill 越来越多时，它会污染整个工作环境。

比如我有一些 Skill 是专门用来做视频内容的，还有一些 Skill 是专门用来生成小红书口播风格、信息卡片、字幕处理和数据复盘的。

这些 Skill 对内容项目很有用，但在其他项目里并不需要。

如果全部放在全局，AI 每次对话时虽然只会读取 Skill 的标题和描述，但当数量多了之后，判断成本会变高。尤其是当两个工具描述很相似时，AI 可能不知道该选哪个，甚至用错工具。

这就会影响当前对话的准确性。

所以我更倾向于把对应的 Skill 放到对应的项目目录里。

也就是说，内容项目需要的 Skill，就放在内容项目里；开发项目需要的 Skill，就放在开发项目里。这样 Skill 只会在对应项目中触发，不会影响其他任务。

## 五、项目级 Skill 放在哪里？

项目级 Skill 通常会放在项目目录下的隐藏文件夹中。

比如在我的项目里，会有一个类似 `.codex` 的隐藏目录，里面再放 `skills` 文件夹。与当前项目相关的 Skill，就放在这个目录下。

需要注意的是，Codex 内置的文件管理器通常看不到以点开头的隐藏文件夹。本地访达默认也看不到。

如果在 Mac 上想查看隐藏文件，可以使用快捷键：

```text
Command + Shift + .
```

这样就可以显示或隐藏这些带点前缀的文件夹。

我会把小红书相关、内容创作相关、字幕处理相关的 Skill 都放在这个项目级目录里。这样它们只服务于当前项目，不会影响其他项目。

## 六、用文件和工作流生成内容大纲

在实际创作时，我不会每次都让 AI 从零开始写稿。

比如我要录一个新视频，我会先告诉 Codex 一个大致想法：我要录什么主题、想表达什么观点、目标受众是谁。

然后 Codex 会根据当前项目里的文件，读取历史口播稿、选题记录、风格说明和数据复盘结果，帮我生成一个适合录制的大纲。

这个大纲通常不会是特别完整、逐字逐句的口播稿。因为我自己录视频时，不太喜欢完全照稿念。我更需要的是一个清晰的结构。

所以它会给我：

一句话结论；
选题建议来源；
为什么这个选题值得录；
口播顺序；
哪些内容不要展开；
哪些句子可以自由发挥。

其中我觉得很有帮助的一点，是它会提醒我不要展开哪些内容。

因为我自己有时候讲东西会比较发散，如果没有边界，很容易把一个视频讲得太散。Codex 会根据我的选题目标，提醒我哪些内容不应该在这一期展开，从而帮助我控制表达范围。

最终，我会基于这个大纲完成视频录制。

## 七、把发布后的数据继续沉淀回项目

录完视频之后，项目还没有结束。

我后面还会有一个数据复盘工作流，让 Codex 通过自动化工具去创作后台获取数据，再补充到项目文件中。

这些数据包括视频表现、互动情况、内容方向反馈等。

同时，我的视频字幕稿也会被整理进项目。因为对于 AI 来说，它不一定需要原始视频，只要有字幕稿，它就能知道这期视频到底讲了什么。

当字幕稿和数据表现结合起来之后，Codex 就可以帮我分析：

这个选题为什么表现好；
这个视频是不是讲得太散；
用户更关注哪一部分；
下一个视频应该优化什么；
哪些方向可以继续做。

这样，每一次发布都不只是一次单独的创作，而是会继续沉淀到项目里，成为下一次创作的参考。

## 八、长期项目管理的关键：让文件成为记忆

我现在越来越觉得，如果想长期使用 Codex 管理一个项目，最重要的不是让它“记住你说过什么”，而是让项目本身变得可读、可复用、可沉淀。

最好的方式，就是通过文件把项目规整成不同目录。

比如：

选题放在选题目录；
口播稿放在脚本目录；
字幕稿放在字幕目录；
数据复盘放在数据目录；
工作流说明放在流程目录；
项目规则写进 `AGENTS.md`；
专用 Skill 放进项目级 Skill 目录。

这样一来，AI 每次进入项目，都能通过读取文件快速恢复上下文，而不是依赖某一次聊天记录。

对于长期项目来说，聊天只是交互入口，文件才是真正的记忆。

## 九、最后总结

如果你只是临时问几个问题，用 Chats 就够了。

但如果你想长期管理一个项目，不管是代码项目、内容项目、创业项目，还是数据复盘项目，我更建议使用 Projects。

在项目里，把重要内容沉淀成文件，把项目说明写进 `AGENTS.md`，把固定流程做成 workflow，把专用能力做成项目级 Skill，而不是全部堆到全局环境里。

这样做的好处是：

每个项目都有自己的上下文；
每个项目都有自己的文件记忆；
每个项目都有自己的专用工具；
不同项目之间不会互相污染；
AI 可以持续基于历史资料进行协作。

Codex 真正适合长期使用的方式，不是把它当成一个单次问答工具，而是把它放进一个结构清晰的项目目录里，让它围绕文件、流程和规则持续工作。

这样，它才更像一个真正能长期协作的项目助手。
