# OpenClaw 入门：为什么它不只是一个 AI 聊天机器人，而是个人 AI 助手框架？

很多人第一次听到 OpenClaw，可能会把它理解成“又一个 AI Chat 应用”。毕竟现在已经有很多 AI 聊天工具了：你可以打开一个网页，输入问题，模型给你回答；也可以使用各种自动化平台，把多个服务串起来完成任务。

但 OpenClaw 的定位不太一样。它更接近一个可以长期运行的个人 AI 助手框架：你可以把它部署在自己的机器或 VPS 上，让它接入 Telegram、WhatsApp、Slack、Discord 这类你已经在用的聊天工具，然后让它帮你处理邮件提醒、日程提醒、每日简报、网页检查、信息检索、文件整理，甚至浏览器自动化等任务。

它最有意思的地方不是“能不能和 AI 聊天”，而是它试图把 AI 从一个被动问答工具，变成一个可以长期在线、能记住上下文、能主动提醒你、能调用工具、能执行定时任务的个人助手。

---

## 1. OpenClaw 解决了什么问题

在 OpenClaw 之前，如果你想做一个个人 AI 助手，大概有几种方式。

第一种，是直接使用 ChatGPT、Claude、Gemini 这类 AI Chat 应用。它们非常适合问答、写作、分析和代码辅助，但它们通常是“你问，它答”。如果你不主动打开它，它一般不会主动在 Telegram 或 WhatsApp 里提醒你今天有哪些会议，也不会每隔一段时间检查你的邮箱或网站状态。

第二种，是使用自动化平台，比如一些工作流工具。它们可以配置触发器、节点、API 调用、条件判断，实现“收到邮件后通知我”“每天早上发送报告”这类自动化。但这类工具通常更像流程编排器，需要你明确设计每一步，体验更偏工程化，而不是像和一个助手自然对话。

第三种，是使用开发者 Agent 或 Coding Agent。它们可以读取文件、修改代码、执行命令，但更多服务于“开发任务”，通常运行在终端或 IDE 里，不太像一个日常生活和工作里的个人助手。

OpenClaw 主要解决的问题是：如何把 AI 模型、聊天渠道、本地工具、文件记忆、定时任务和主动提醒组合成一个长期运行的个人 AI 助手。

它适合这些场景：

- 每天早上通过 Telegram 收到日程、天气、新闻和待办简报。
- 监控邮箱，如果有重要邮件就提醒你。
- 会议开始前自动发会议链接。
- 定期检查网站、项目、日志或服务器状态。
- 把聊天中提到的重要信息写入长期记忆。
- 根据你的工作习惯自动建议脚本或自动化。
- 通过浏览器工具检查网页、填写表单、下载文件。
- 把多个聊天渠道统一接入一个 AI 助手。

它不适合这些场景：

- 只是偶尔问几个问题，用普通 AI Chat 就够了。
- 对安全性要求极高，但还没做好隔离和权限控制。
- 希望完全无配置、完全托管、完全不用理解底层机制。
- 不愿意管理 API Key、部署环境、Token 成本和数据权限。
- 想让 AI 直接接管重要账号、敏感数据或高风险操作。

OpenClaw 的价值在于“长期运行 + 多渠道接入 + 工具调用 + 主动任务 + 记忆”，而不是单次问答。

## 2. OpenClaw 是什么：基本概念介绍

简单理解，OpenClaw 是一个可以自托管的个人 AI 助手运行时。

它不是一个单纯的网页聊天框，也不是单纯的自动化平台，而是由几个核心部分组成。

### Gateway：消息入口和运行中心

Gateway 可以理解为 OpenClaw 的核心服务。你需要把它运行在某个地方，比如：

- 本机。
- Mac mini。
- VPS。
- Docker 环境。
- 云服务器。

Telegram、WhatsApp、Slack、Discord 等渠道发来的消息，都会进入这个 Gateway。

Gateway 收到消息之后，会做几件事：

1. 找到这条消息属于哪个 session。
2. 读取相关上下文。
3. 把用户消息、系统提示词、workspace 文件、工具信息、技能信息等拼成完整上下文。
4. 发给你配置的 AI 模型。
5. 如果模型要求调用工具，就执行工具。
6. 把工具结果再发回模型。
7. 最后把模型回复发送回对应聊天渠道。

所以 Gateway 不只是“转发消息”，它还负责上下文管理、工具调用、会话管理和响应路由。

### Channel：聊天渠道

Channel 就是你和助手交互的入口。

比如：

- Telegram。
- WhatsApp。
- Slack。
- Discord。
- Dashboard Chat。

这也是 OpenClaw 和普通 AI Chat 应用的一个重要区别。它不是要求你每天打开一个新 App，而是把 AI 助手接入你已经在用的聊天软件。

你可以在 Telegram 里问它：

```txt
今天有什么安排？
```

也可以让它每天早上主动给你发：

```txt
今日简报：
- 日程
- 天气
- 重要邮件
- 行业新闻
- 建议优先事项
```

### Model：真正负责推理的 AI 模型

OpenClaw 本身不是大模型。它需要连接模型供应商，比如：

- OpenAI。
- Anthropic。
- Google Gemini。
- 其他兼容模型。

你可以选择一个默认模型，也可以为不同任务配置不同模型。

比如：

- 普通提醒使用便宜模型。
- 深度分析使用更强模型。
- 编码任务使用适合代码的模型。
- 图片任务使用图像模型。

OpenClaw 更像是模型上层的“助手运行框架”。

### Workspace：助手的工作目录和文件记忆

OpenClaw 会有一个 workspace 目录。这个目录很关键。

它里面通常会有一些 Markdown 文件，比如：

```txt
AGENTS.md
SOUL.md
USER.md
IDENTITY.md
TOOLS.md
HEARTBEAT.md
MEMORY.md
memory/YYYY/MM/DD.md
```

这些文件会影响助手的行为。

比如：

- `SOUL.md` 定义助手的语气、性格、边界。
- `USER.md` 描述它正在帮助谁。
- `AGENTS.md` 描述通用规则、记忆规则、工具规则。
- `HEARTBEAT.md` 描述周期性检查任务。
- `MEMORY.md` 保存长期记忆。
- 每日 memory 文件保存当天日志。

你可以把 workspace 理解成助手的“磁盘大脑”。它不是模型参数里的记忆，而是以文件形式保存的上下文。

### Tools：工具调用能力

OpenClaw 的强大之处在于，它不只是聊天，还可以调用工具。

比如：

- 读取文件。
- 写入文件。
- 修改文件。
- 执行 shell 命令。
- fetch 网页。
- 搜索网页。
- 控制浏览器。
- 管理后台进程。
- 查询 memory。
- 触发 cron。
- 管理 session。

模型本身不会真的去执行命令，它只是“决定要调用哪个工具”。真正执行工具的是 Gateway。

### Cron 和 Heartbeat：主动性的来源

OpenClaw 能主动提醒你，核心靠两类机制：

- Cron：明确时间点的定时任务。
- Heartbeat：周期性的轻量检查。

比如：

```txt
每天早上 8 点给我发送科技新闻简报
```

这适合 Cron。

而：

```txt
定期检查我的邮箱，如果有重要客户邮件就提醒我
```

这更适合 Heartbeat。

Cron 更像“到点执行任务”，Heartbeat 更像“周期性扫描有没有需要提醒的事情”。

### Skills：可复用能力包

Skill 可以理解成一组可复用的指令和知识。

比如你经常让助手帮你做代码 review，就可以把“如何做代码 review”整理成一个 skill。以后模型需要这个能力时，可以把对应 skill 加载到上下文里，而不是每次都把一大段提示词重新发给它。

Skill 的价值是：按需加载上下文，避免每次都把所有规则塞进模型。

### Session：会话管理

Session 负责记录一段对话的历史。

比如你在 Telegram 里连续聊天，OpenClaw 需要知道这些消息属于同一段对话，这样模型才能理解上下文。

如果你同时接入 WhatsApp、Telegram、Slack，就需要决定：

- 它们是否共享同一个 main session。
- 群聊是否应该单独隔离。
- 多个用户是否要分开 session。
- cron 任务是否使用独立 session。

Session 解决的是“上下文属于谁”的问题。

### Memory：长期记忆

OpenClaw 的 memory 不是玄学，它本质上就是写入 workspace 里的 Markdown 文件。

比如你告诉它：

```txt
请记住，我平时喜欢早上处理重要任务，下午处理会议。
```

它可以把这条信息写入 `MEMORY.md`。

之后新 session 开始时，它可以读取这个文件，让模型重新知道这个事实。

## 3. 最简单的使用方式

最小使用方式可以概括为三步：

1. 部署 OpenClaw。
2. 配置模型。
3. 接入一个聊天渠道。

假设已经在一台服务器上安装好 OpenClaw，最核心的是启动 Gateway。

示例命令大概类似：

```bash
openclaw gateway
```

这个命令的作用是启动 OpenClaw 的核心服务。只要 Gateway 运行着，Telegram、Dashboard 或其他渠道的消息才能进入 OpenClaw。

然后你需要配置模型 API Key。比如使用 OpenAI：

```txt
Provider: OpenAI
API Key: sk-...
Model: gpt-4.1 / gpt-5.x / other model
```

再配置 Telegram Bot。

Telegram 一般需要通过 BotFather 创建一个 bot，拿到 token，然后把 token 配置到 OpenClaw 中。

配置完成之后，你可以在 Telegram 里发：

```txt
Hi, what model are you using?
```

消息会经过这样的路径：

```txt
Telegram
  -> OpenClaw Gateway
  -> Context Assembly
  -> AI Model
  -> Gateway
  -> Telegram
```

这个例子能帮助你理解 OpenClaw 的基本原理：你不是直接和模型说话，而是通过 OpenClaw 的 Gateway 和模型交互。Gateway 会在中间加入上下文、管理 session、调用工具，并把结果发回聊天应用。

不过这还不是完整用法。真正有价值的是后面的 workspace、tools、memory、cron、heartbeat 和 skills。

## 4. 核心流程是怎么跑起来的

一次完整的 OpenClaw 交互，大致可以分成几个步骤。

### 1. 用户从聊天渠道发送消息

比如你在 Telegram 里发：

```txt
帮我看看今天有什么安排。
```

这条消息先进入 Telegram Bot，再转给 OpenClaw Gateway。

### 2. Gateway 判断 session

Gateway 会判断这条消息属于哪个会话。

如果你是在主 Telegram 私聊里发的，它可能属于 main session。

如果是在群聊里发的，它可能属于单独的 group session。

如果是 cron 任务触发的，它可能属于 cron session。

### 3. OpenClaw 组装上下文

接着，OpenClaw 会组装要发给模型的上下文。

上下文通常包括：

- 系统提示词。
- 当前时间。
- 工具列表。
- 可用 skills。
- workspace 信息。
- `AGENTS.md`。
- `SOUL.md`。
- `USER.md`。
- `HEARTBEAT.md`。
- 近期 memory。
- 当前 session 历史消息。
- 用户刚刚发的消息。

这一步非常关键，因为模型最终能做什么，很大程度取决于它看到的上下文。

### 4. 请求发送给 AI 模型

OpenClaw 把完整上下文发给你配置的模型。

模型开始推理。

如果问题很简单，比如：

```txt
1 + 1 是多少？
```

模型可能直接回答。

如果问题需要工具，比如：

```txt
帮我抓取这个网页内容并总结。
```

模型可能会要求调用 `web_fetch` 工具。

### 5. Gateway 执行工具

模型不会自己访问网页，也不会自己读取文件。它只会返回“我需要调用某个工具”的意图。

Gateway 收到工具调用请求后，真正执行工具。

比如：

```txt
web_fetch("https://example.com")
```

执行后，Gateway 得到网页内容。

### 6. 工具结果返回给模型

Gateway 把工具结果再发给模型。

模型基于工具结果继续分析。

如果还需要其他工具，可能继续进入下一轮。

### 7. 生成最终回复

当模型不再需要工具时，就会输出最终结果。

Gateway 再把结果发回 Telegram、WhatsApp 或其他来源渠道。

### 8. 记录 transcript 或 memory

最后，OpenClaw 可能会保存这次对话的 transcript。

如果模型认为有重要信息需要记忆，也可能写入 daily log 或 `MEMORY.md`。

这就是 OpenClaw 的核心 agent loop。

## 5. 常用能力介绍

### 5.1 Gateway：启动和保持在线

Gateway 是 OpenClaw 的核心运行进程。

最简单启动方式：

```bash
openclaw gateway
```

但如果你关闭终端，这个进程可能就停了。所以真实使用时，通常需要让它长期运行。

比如可以用 `tmux`：

```bash
tmux new -s claw
openclaw gateway
```

然后按：

```txt
Ctrl + B
D
```

这样 Gateway 会留在后台运行。

Gateway 必须持续在线，否则：

- Telegram 消息无法处理。
- cron 不会执行。
- heartbeat 不会检查。
- dashboard 可能无法访问。

### 5.2 Dashboard：控制台和调试入口

OpenClaw 一般会提供一个 Dashboard，也可以叫 Control UI。

Dashboard 里可以做很多事：

- 直接聊天。
- 查看日志。
- 查看 agent。
- 修改 workspace 文件。
- 查看工具调用。
- 查看 session。
- 查看 cron jobs。
- 配置模型。
- 配置 web search。
- 查看 channel。
- 调试错误。

比如你在 Telegram 里发了一句话，但没有收到回复，可以去 Dashboard 的 logs 或 chat 页面查看：

- 消息是否进入 Gateway。
- 模型是否返回。
- 是否调用了工具。
- 工具是否失败。
- Telegram 回传是否失败。

Dashboard 对初学者非常重要，因为它能让你看到“模型背后到底做了什么”。

### 5.3 Workspace 文件：塑造助手行为

Workspace 是 OpenClaw 最值得理解的部分之一。

比如 `SOUL.md` 可以写助手的性格和行为边界：

```md
# SOUL

你是一个主动、可靠、简洁的个人 AI 助手。

原则：
- 不要说空话，直接帮用户解决问题。
- 不确定时先说明不确定。
- 涉及敏感操作时必须先确认。
- 保护用户隐私，不在群聊中泄露私人信息。
```

`USER.md` 可以写用户信息：

```md
# USER

用户是一名前端开发者，关注 Next.js、React、Web3 前端工程化。
用户喜欢直接、清晰、有工程落地感的回答。
```

`MEMORY.md` 可以写长期记忆：

```md
# MEMORY

- 用户目前正在系统练习前端工程化 demo。
- 用户关注 Web3 前端、表格工程化、交易状态机和表单工程化。
```

这些文件会影响模型回答。

需要注意的是，修改这些文件后，最好开启一个新 session，让新的文件内容重新注入上下文。

比如在聊天里发送：

```txt
/new
```

### 5.4 Tools：让 AI 从“回答”变成“做事”

OpenClaw 的 tools 让助手可以执行动作。

常见工具包括：

```txt
read
write
edit
patch
shell
web_fetch
web_search
browser
memory_search
memory_get
cron
```

比如你让它：

```txt
帮我创建一个简单的 HTML 页面。
```

模型可能会调用 `write` 工具，在 workspace 里写入：

```txt
index.html
```

如果你让它：

```txt
抓取 example.com 并总结。
```

它可能会调用 `web_fetch`。

如果你让它：

```txt
搜索今天的 AI 新闻。
```

它可能需要 `web_search`。这通常需要配置搜索服务 API Key，比如 Brave Search 或 Perplexity。

这里的关键点是：工具能力越强，风险也越高。

尤其是：

- shell。
- browser。
- 文件编辑。
- 邮件发送。
- 日历修改。
- 外部 API 调用。

这些工具最好先在隔离环境里测试，不要一开始就连接重要账号。

### 5.5 Cron：明确时间的定时任务

Cron 适合“确定时间点”触发的任务。

比如：

```txt
每天早上 8 点给我发送科技新闻简报。
```

OpenClaw 可以把它转换成一个 cron job。

这个 cron job 到时间后，会自动向模型发起一次 agent run。

它和你手动发消息类似，只不过触发者不是你，而是系统定时器。

适合 cron 的任务：

- 每天早上发送简报。
- 每周五总结本周工作。
- 20 分钟后提醒我。
- 每天晚上整理当天日志。
- 每周生成一次项目健康报告。

Cron 的特点是：时间明确，通常期待有输出。

### 5.6 Heartbeat：周期性安静检查

Heartbeat 更像周期性后台检查。

比如你在 `HEARTBEAT.md` 里写：

```md
# HEARTBEAT

- 检查是否有需要提醒用户的日程。
- 检查是否有重要邮件。
- 如果没有需要用户注意的事情，保持安静。
```

OpenClaw 可以每隔一段时间执行一次 heartbeat。

它和 cron 的区别是：heartbeat 不一定要给你发消息。

如果没有重要事情，它可以只返回：

```txt
heartbeat ok
```

然后 OpenClaw 不打扰你。

适合 heartbeat 的任务：

- 定期检查邮箱。
- 定期检查日程。
- 检查网站是否异常。
- 检查项目状态。
- 检查是否有阻塞任务。
- 轻量关怀提醒。

Heartbeat 的特点是：周期性监控，有事才打扰。

### 5.7 Skills：把重复提示词变成能力包

如果你经常让助手做同一种任务，不应该每次都写一大段 prompt。

比如你经常要求它按某种规范写 git commit，可以创建一个 skill：

```md
# Git Commit Skill

当用户要求创建 commit message 时：
1. 使用 conventional commits 格式；
2. 类型只能是 feat、fix、docs、style、refactor、test、chore；
3. 标题不超过 72 字符；
4. 如果有多项变更，提供 body；
5. 不要编造不存在的变更。
```

这样模型在相关任务中可以加载这个 skill。

Skill 的好处是：

- 可复用。
- 可共享。
- 可按需加载。
- 不污染每次对话上下文。
- 适合沉淀工作流知识。

不过第三方 skills 要谨慎。因为它们本质上是会影响模型行为的指令和文件，最好先阅读内容再启用。

### 5.8 Memory：让助手记住你

OpenClaw 的 memory 本质是 Markdown 文件。

你可以告诉它：

```txt
请记住：我每天上午更适合处理深度工作，下午适合开会。
```

它可以写入 `MEMORY.md`。

长期记忆适合保存：

- 用户偏好。
- 工作习惯。
- 项目背景。
- 常用账号说明。
- 不敏感的个人上下文。
- 长期目标。
- 已经确认的规则。

每日日志适合保存：

- 今天发生了什么。
- 当前任务进展。
- 临时上下文。
- 当天决策。
- 待跟进事项。

需要注意：不要把敏感信息随便放入 memory，比如密码、私钥、支付信息、重要 token。

## 6. 在真实业务里一般怎么组合使用

OpenClaw 在真实使用中，通常不是只靠一个功能，而是多个能力组合。

比如做一个“个人工作助手”，可以这样组合：

```txt
Telegram Channel
  -> 日常聊天和接收提醒
OpenAI / Anthropic Model
  -> 推理和自然语言处理
Workspace
  -> 保存助手规则、用户信息、长期记忆
Tools
  -> 读取文件、抓网页、执行脚本
Cron
  -> 每日简报、每周总结
Heartbeat
  -> 邮箱、日程、网站状态检查
Skills
  -> 代码 review、日报总结、研究报告、邮件草稿
Dashboard
  -> 调试、查看日志、修改配置
```

一个典型场景是每日简报。

你可以对 OpenClaw 说：

```txt
每天早上 8 点给我发一份工作简报，包括今天日程、重要邮件、天气、AI 行业新闻和三个建议优先事项。
```

OpenClaw 可能会创建 cron job。

到时间后，它会：

1. 触发定时任务。
2. 读取当前日期和上下文。
3. 调用日历工具。
4. 调用邮件工具。
5. 调用 web search。
6. 整理成简报。
7. 发送到 Telegram。

另一个场景是重要邮件提醒。

你可以在 heartbeat 中加入：

```txt
如果有重要客户邮件或会议变更，请提醒我。
```

每隔一段时间，它会检查一次。如果没事，就保持安静；如果发现重要邮件，就发消息给你。

再比如知识管理。

你可以让它：

```txt
请总结我们这周关于 Next.js 工程化的讨论，把重要结论写入长期记忆。
```

它可以把总结写入 `MEMORY.md`，以后新会话也能继续参考。

## 7. 常见误区和使用边界

### 误区一：以为 OpenClaw 只是另一个聊天机器人

OpenClaw 的重点不是聊天，而是长期运行的 agent runtime。

如果你只用它问：

```txt
React useEffect 是什么？
```

那它和普通 AI Chat 差别不大。

它真正有价值的地方是：

- 接入已有聊天应用。
- 调用本地工具。
- 记录长期记忆。
- 定时执行任务。
- 主动提醒。
- 操作文件和浏览器。
- 在多个渠道之间维持 session。

### 误区二：一开始就连接重要账号

OpenClaw 很强，但也意味着权限风险更高。

如果你给它：

- 邮箱权限。
- 日历权限。
- 浏览器权限。
- shell 权限。
- 文件系统权限。
- 重要 API Key。

它就可能在模型判断错误、prompt 注入或工具误用时做出不该做的事情。

更合理的做法是：

1. 先跑在 VPS 或隔离机器上。
2. 只连接测试账号。
3. 只给最小权限。
4. 先关闭高风险工具。
5. 熟悉日志和工具调用。
6. 再逐步扩大能力范围。

### 误区三：把 workspace 当成安全沙箱

Workspace 是默认工作目录，但不一定是硬沙箱。

也就是说，工具通常会以 workspace 为当前目录执行，但如果没有额外隔离，绝对路径仍然可能访问其他位置。

所以不要以为：

```txt
文件放在 workspace 外就绝对安全
```

如果要做更严格隔离，需要额外使用容器、权限控制、沙箱配置或独立 VPS。

### 误区四：以为 memory 会自动完美工作

Memory 不是模型“真的记住了”，而是写入文件，然后在后续会话中重新读取。

如果重要信息没有写入文件，它就不会长期存在。

所以想让它记住什么，最好明确说：

```txt
请把这条写入长期记忆。
```

或者：

```txt
请总结这次对话中值得长期保留的内容，写入 MEMORY.md。
```

不要完全依赖模型自动判断。

### 误区五：滥用 heartbeat

Heartbeat 很有用，但它会周期性触发模型调用。

如果你把大量任务放进 heartbeat，并且频率很高，就会带来：

- Token 成本上升。
- 上下文膨胀。
- 无意义检查过多。
- 频繁打扰。
- 调试困难。

适合 heartbeat 的是“轻量、周期性、没事就静默”的检查。

如果任务需要明确时间、明确输出，应该用 cron。

### 误区六：所有任务都用同一个强模型

OpenClaw 可能会频繁调用模型。如果所有任务都用最贵的模型，成本会比较高。

更合理的方式是：

- 普通提醒用便宜模型。
- 深度分析用强模型。
- 代码任务用代码模型。
- 长文本总结用适合长上下文的模型。
- 图像任务用图像模型。

OpenClaw 的优势之一就是可以组合不同模型，不必被单一模型绑定。

### 误区七：忽略 session 隔离

如果只有你一个人用，一个 main session 通常没问题。

但如果你把助手放进群聊，或者让多个人都能 DM 它，就必须注意 session 隔离。

否则可能出现：

- A 的私人信息被 B 问出来。
- 群聊读取到私人上下文。
- 不同渠道的会话混在一起。
- cron 任务带入不相关上下文。

多用户场景下，一定要认真配置 session scope。

## 8. 一个更完整的示例：配置一个每日简报 + 心跳检查助手

下面用一个简化示例说明如何把 OpenClaw 配成一个基础个人助手。

### 8.1 SOUL.md：定义助手风格

```md
# SOUL

你是一个可靠、主动、克制的个人 AI 助手。

行为原则：
- 直接给出有用信息，不要说空话。
- 不确定时明确说明不确定。
- 涉及发送邮件、修改日历、执行命令等操作时，必须先请求确认。
- 默认保护用户隐私，不在群聊中透露私人信息。
- 如果没有重要事情，不要主动打扰用户。
```

这个文件控制助手的整体语气和边界。

它不是任务指令，而是长期人格和行为约束。

### 8.2 USER.md：描述用户背景

```md
# USER

用户是一名前端开发者，主要关注：
- React
- Next.js
- TypeScript
- 前端工程化
- Web3 前端开发

用户偏好：
- 回答要直接、清楚、有工程落地感。
- 技术解释要先讲为什么，再讲怎么做。
- 不喜欢空泛建议。
```

这个文件帮助助手理解“它正在服务谁”。

后续它写简报、建议任务、总结资料时，会更贴近用户背景。

### 8.3 HEARTBEAT.md：配置周期性检查

```md
# HEARTBEAT

周期性检查以下事项：
1. 是否有即将开始的会议。
2. 是否有明显重要或紧急的邮件。
3. 是否有用户正在进行的项目需要提醒。
4. 如果没有需要用户注意的事情，回复 heartbeat ok，不要打扰用户。
```

这个文件适合放“有事才提醒”的任务。

比如会议提醒、邮件提醒、项目阻塞提醒。

### 8.4 MEMORY.md：保存长期记忆

```md
# MEMORY

## 用户长期偏好

- 用户更关注前端工程化能力，而不只是库的 API 用法。
- 用户正在系统练习多个工程化 demo。
- 用户希望技术文章适合发布到掘金、CSDN、登链社区或个人博客。
```

这个文件保存长期有价值的事实。

它不应该变成流水账。

流水账更适合每日 memory 文件。

### 8.5 创建一个每日简报 cron

你可以直接在聊天里说：

```txt
每天早上 8 点给我发送一份技术简报，包括：
1. 今天日程；
2. 重要邮件；
3. 前端和 AI 工具相关的重要新闻；
4. 今天建议优先处理的 3 件事。
```

OpenClaw 可以基于这段自然语言创建 cron。

这个任务适合 cron，因为它有明确时间，并且你期待每天收到输出。

### 8.6 让助手沉淀记忆

当你和助手讨论完一个重要项目后，可以说：

```txt
请总结这次对话中值得长期保留的信息，写入 MEMORY.md。
同时把今天的临时进展写入今天的 daily log。
```

这样它可以分别处理：

- 长期记忆。
- 当天日志。

这比让模型自己随缘记忆更可靠。

## 9. 学习和落地建议

学习 OpenClaw，建议不要一上来就连接所有账号，也不要一开始就追求复杂自动化。

可以按这个顺序来。

第一步，只理解基本结构。

先搞清楚：

```txt
Channel -> Gateway -> Context -> Model -> Tools -> Response
```

这条链路非常重要。

第二步，只接入一个聊天渠道。

建议先用 Telegram 或 Dashboard Chat。

不要一开始同时接入 WhatsApp、Slack、Discord。

第三步，只配置一个模型。

先用一个成本可控的模型跑通流程。

等熟悉之后，再考虑多模型策略。

第四步，熟悉 Dashboard。

重点看：

- logs。
- chat。
- tool calls。
- agents。
- files。
- cron jobs。
- config。

Dashboard 是你理解 OpenClaw 的最好入口。

第五步，修改 workspace 文件。

先改：

```txt
SOUL.md
USER.md
AGENTS.md
HEARTBEAT.md
```

观察助手回答风格和行为是否变化。

第六步，练习 tools。

可以从低风险工具开始：

- `web_fetch`。
- `read`。
- `write workspace 文件`。

暂时不要急着开放 shell、浏览器控制、重要账号权限。

第七步，创建一个简单 cron。

比如：

```txt
每天早上 9 点提醒我查看今天的任务。
```

先确认 cron 能正常运行。

第八步，配置一个 heartbeat。

比如：

```txt
每隔一段时间检查是否有需要提醒我的事项，没有就保持安静。
```

理解它和 cron 的区别。

第九步，练习 memory。

明确告诉它：

```txt
请把这条写入长期记忆。
```

然后去 `MEMORY.md` 里确认它是否真的写入。

第十步，再考虑真实账号和复杂能力。

比如：

- 邮箱。
- 日历。
- 浏览器。
- GitHub。
- Notion。
- 服务器监控。
- 多 agent。
- voice mode。

这些都应该在你理解权限和安全边界后再做。

## 10. 总结

OpenClaw 最核心的价值，不是让你多一个聊天窗口，而是让 AI 变成一个可以长期在线、接入真实工具、拥有文件记忆、能主动提醒、能周期性执行任务的个人助手。

它和普通 AI Chat 的区别在于：普通 AI Chat 更偏“问答”；OpenClaw 更偏“助手运行时”。

它和传统自动化平台的区别在于：传统自动化平台更偏“流程编排”；OpenClaw 更偏“自然语言驱动的个人 agent”。

初学者最应该先记住这几个概念：

```txt
Gateway：核心运行入口
Channel：聊天渠道
Workspace：助手的文件大脑
Context：每次发给模型的完整上下文
Tools：让模型能做事
Cron：固定时间执行任务
Heartbeat：周期性安静检查
Skills：可复用能力包
Session：会话隔离和历史
Memory：长期记忆文件
```

真正使用 OpenClaw 时，安全边界非常重要。不要一开始就给它接入重要账号，也不要直接让它操作敏感数据。更好的方式是先在 VPS 或隔离环境中测试，逐步理解它如何组装上下文、如何调用工具、如何记录 memory、如何执行 cron 和 heartbeat。

当你理解这些之后，OpenClaw 就不再只是一个新鲜 AI 工具，而是一个可以被不断配置、训练、扩展的个人 AI 助手系统。它的潜力也正在这里：不是替你回答一次问题，而是在你的日常工作和生活流程中，逐渐变成一个长期协作的智能助手。
