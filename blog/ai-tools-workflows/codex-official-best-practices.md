# Codex 官方最佳实践解读：如何更高效地管理线程、工具、自动化和长期项目

最近 Codex 官方团队发布了一篇文章，叫做 **Getting the most out of Codex**，主要讲的是如何更高效地使用 Codex，以及在实际工作中有哪些最佳实践。

这篇文章不是单纯介绍功能，而是更偏向“怎么用 Codex 才能发挥出更好的效果”。所以今天我想结合官方文章里的内容，再加上我自己日常使用 Codex 的经验，整理一篇更适合普通用户和开发者理解的实操笔记。

无论你是用 Codex 写代码、做内容、处理文档，还是做调研、自动化和项目管理，这些方法都能提升使用效率。

## 一、线程：独立任务最好新开话题

在 Codex 里，每一个独立对话都可以理解为一个线程，也就是一个话题。

这个概念其实很好理解。我们在豆包、ChatGPT 或者其他 AI 应用里，也经常会看到左侧一条一条的对话记录。每一条独立对话，本质上就是一个独立话题。

需要注意的是，话题和话题之间不会共享对话信息。

所以，如果是一个新的独立任务，最好新开一个新话题。这样做有两个好处：

第一，上下文更干净。
第二，上下文更短时，AI 的执行效果通常会更好。

如果一个话题里塞了太多无关信息，AI 后面处理任务时就可能被之前的上下文干扰，甚至出现方向跑偏的问题。

当然，如果某一个话题你需要长期使用，也可以把它 pin 到顶部。

比如我自己会把一些长期需要复用的对话固定到上方。因为我之前在这些话题里给过 AI 一些小红书相关的信息，如果后面我要让它帮我写选题、做视频内容、剪视频或者生成主题，我就会自然回到这个固定话题里。

这是一种使用方式：长期在同一个线程里对话，让压缩后的上下文也成为这个主题的一部分。

另一种方式是把信息放到项目文件里，让 AI 每次进入项目时重新读取相关资料。两种方式都可以，关键看你这个任务更适合“长期对话”，还是更适合“文件化管理”。

## 二、语音输入：让 Web Coding 更顺手

Codex 自带语音输入功能。

在输入框右下角，有一个语音按钮。点击之后，可以直接说话，比如“帮我看看这个视频做得怎么样”。Codex 会调用 OpenAI 自己的模型，把语音转成文字。

如果本地没有安装其他语音输入工具，用 Codex 自带的就已经够用了。

但如果你本地有更顺手的语音输入工具，效率会更高。比如我自己用的是闪电类的语音输入工具，按住右侧 Option 键就能触发。除此之外，还有一些基于 Whisper 的语音输入工具。

我认为，对于 Web Coding 或者复杂任务描述来说，语音输入是非常明显的效率提升。

因为很多时候，我们不是不会写 prompt，而是打字太慢。尤其是要描述页面效果、交互逻辑、修改需求时，直接说出来会比手打快很多。

## 三、对话队列和 steer：任务执行中也能插队修改方向

Codex 还有一个很实用的机制，就是对话队列。

当 Codex 正在执行任务时，如果你继续发送一条新消息，这条消息默认会进入队列。也就是说，它会等当前任务完成后，再继续执行下一条。

这个设计很适合连续任务。

比如你先让它实现一段代码，然后你又提前发一条消息，让它实现完之后帮你 review 代码。这样你就不用一直盯着它。它写完代码之后，会继续执行下一条 review 任务。

除了排队，Codex 还有一个 steer 功能。

steer 可以理解成“插队纠偏”。如果 AI 正在执行任务，你发现它方向不对，可以把新的指令 steer 进去。它会在上一次发言或工具调用结束后，把你的新指令插入进去。

这和立即打断不完全一样。

它不是在工具调用中间硬生生终止，而是在当前最后一次工具调用或发言结束后，把新的指令接上。

这个功能适合在 AI 执行过程中及时调整方向，比如：

“别看这个文件了，换另一个。”
“这个方向不对，先停下来。”
“不要继续实现，先解释一下方案。”
“刚才那个需求理解错了，按这个版本改。”

对于长任务来说，steer 非常有用。它可以避免 AI 沿着错误方向跑太久。

## 四、Codex 的调研和自动化工具

Codex 内置了一些工具，可以帮助我们做调研、浏览网页、控制浏览器，甚至控制电脑。

首先是联网调研工具。

如果我们想让 Codex 调研一个主题，可以直接在指令里明确写“调研”两个字。比如：

```text
帮我调研一下最近 AI 视频工具的发展趋势。
```

这时它通常会调用内置的 search the web，也就是联网调研工具。

如果我们需要准确的信息源，就可以让它使用这个工具去搜索和整理资料。

但是，如果你想让 Codex 获取一些需要登录态的平台信息，比如小红书、抖音、后台数据等，普通联网搜索就不够了。这个时候可以使用浏览器自动化工具。

比如通过 `/chrome` 让 Codex 打开浏览器，并基于当前登录状态去访问网页、点击页面、读取内容。

## 五、浏览器工具优先于 Computer Use

Codex 也支持 Computer Use，也就是控制电脑的能力。

安装之后，它可以直接操作你的电脑，比如打开飞书发送消息、打开剪辑软件导出视频、操作某个桌面应用等。

但这里有一个使用原则：

如果你只是想控制浏览器，就不要优先用 Computer Use，而是优先使用浏览器控制工具。

因为 Computer Use 更像一个兜底方案。它能做的事情更多，但成本也更高，执行也可能更慢。

如果任务本身发生在浏览器里，比如打开网页、点击按钮、读取页面、填写表单，那么使用 Chrome 浏览器自动化工具会更合适。

简单来说：

浏览器任务，优先用浏览器工具；
桌面软件任务，再考虑 Computer Use；
能用低成本工具解决，就不要直接上最重的工具。

这样效率会更高，执行也更稳定。

## 六、MCP 和 Skill：给 Codex 接入更多外部能力

除了内置工具，Codex 还可以通过 MCP 接入更多外部服务。

在设置里可以配置 MCP Server。我自己会配置一些开发相关的 MCP，比如 LangSmith、Supabase、MongoDB 等。

这些工具可以帮助 Codex 快速获取外部信息，比如数据库结构、日志、接口状态、项目观测数据等。

除了 MCP，也可以安装 Skill。

Skill 可以搭配相关产品的 CLI 使用。比如飞书 CLI，就可以让 Codex 去控制飞书，完成发消息、写文档、读取云文档等操作。

对于长期项目来说，MCP 和 Skill 的作用非常大。它们可以让 Codex 不只是在本地代码或文档里工作，还能连接外部系统，成为一个真正的自动化协作助手。

## 七、Work from Anywhere：移动端远程工作

官方还提到一个功能叫 Work from Anywhere。

它的意思是，你可以使用 Codex 的移动端应用，在任何地方进行远程工作。

这个功能入口在左侧，需要下载对应应用后才能进行远程控制。

不过这里有一个现实问题：这个应用在国区可能不一定能下载到。如果你需要使用，可能需要美区或者其他地区的账号。

这个功能适合一些轻量远程任务，比如出门在外时，让 Codex 继续跑代码、改文档、查资料，或者检查某个任务进度。

## 八、Automation：定时执行自动化任务

Codex 里还有 Automation，也就是自动化任务。

在左侧可以看到一个小闹钟图标，点进去就是 automation。它可以让 Codex 在指定时间自动执行某些任务。

比如你可以创建一个任务：

每天早上十点，调研小红书今天有什么热门话题。

创建时可以选择任务标题、运行位置、项目目录和执行时间。

这里有一个需要注意的点：Automation 默认选择的模型，不一定是你平时正常对话时使用的模型。

所以创建自动化任务时，一定要看一下模型选择。否则可能会不小心用到一个能力没那么强的模型去做复杂调研。

Automation 还提供了一些官方模板，比如 bug 排查、总结 Git 信息、写日报等。

如果你有固定重复任务，比如日报、周报、数据抓取、竞品调研、内容复盘，Automation 是一个很适合的功能。

## 九、Goals：让 Codex 长时间稳定执行一个目标

Goals 是一个很重要的功能。

它的作用是给 Codex 设置一个长期目标，让它围绕这个目标持续执行任务。

和普通 prompt 不同的是，Goals 会在 Agent 层面持续提醒它当前目标是什么，并检查目标是否完成。

如果只是普通对话，任务执行时间一长，上下文变长之后，AI 可能会开始偷懒，或者逐渐偏离最初目标。

但如果使用 Goals，并且设置了明确的评估标准，它就会更稳定地完成长任务。

开启 Goals 需要在 Codex 的配置里设置。路径大致是：进入 Settings，找到 Configuration，打开 config 文件，把 feature 里的 goals 设置为 true。

之后就可以通过 `/goal` 设置目标。

不过这里有一个关键点：Goals 一定要写清楚评估标准。

比如不要只说：

```text
帮我调研 AI 工具。
```

这样太泛了。

更好的写法是：

```text
请调研全网 AI 视频生成工具，报告不少于 5 万字，必须覆盖产品定位、核心功能、价格、适合用户、优缺点、竞品对比和未来趋势。完成这些内容后再停止。
```

这样它就知道什么时候算完成，什么时候还需要继续做。

Goals 适合非常长的任务，比如深度报告、复杂代码迁移、大规模重构、跨平台调研等。

## 十、Side Panel：不污染主线程的旁路对话

Codex 里还有一个很实用的功能，叫 Side Panel。

可以理解成右侧独立对话。

当左侧主线程正在执行任务时，如果你想临时问一些问题，但又不想污染主线程上下文，就可以打开 Side Panel。

比如左侧正在做一个调研任务，你突然想问：

“Codex Cloud 和 Codex 本地哪个更适合这个场景？”

这个问题和当前任务有关，但你又不希望它进入主线程，影响后续调研。这时就可以在右侧 Side Panel 里问。

Side Panel 会继承左侧已有上下文，但你在右侧发送的信息不会进入左侧主线程。

也就是说，它适合临时追问、旁路讨论、快速解释。

不过需要注意的是，Side Panel 不适合作为长期话题使用。长时间不用可能会过期，也不会在左侧生成一个新的固定话题。所以它更适合临时使用，而不是长期沉淀。

## 十一、右侧预览：Markdown、HTML、截图和评论

Codex 的右侧区域还可以用来预览很多内容。

比如你生成了一个 HTML 页面，点击后可以直接在右侧浏览器里打开。Markdown 文件也可以直接预览。

这对于写报告、做页面、调试前端非常方便。

右侧浏览器里还有一些辅助功能，比如快速截图、添加标注评论等。

比如你看到某段文案不好，可以直接在预览页面上加评论，然后发送给左侧主线程。Codex 就会根据你的标注继续修改。

这比单纯用文字描述“第三段不好”要更直观。

## 十二、共享记忆：我更推荐文件化管理

官方文章里还提到了共享记忆。

因为不同线程之间上下文是独立的，如果想跨线程共享信息，就需要一种外部记忆。

官方提到的是使用 Obsidian vault 这一类云端或文件化服务。

但从我自己的使用体验来看，本质上不一定非要使用某一种特殊记忆服务。只要是结构清晰的 Markdown 文档、项目文档、云文档，都可以成为 Codex 的记忆。

比如你可以把人设、项目信息、业务规则、写作风格、历史数据写成 Markdown 文件，放在项目目录里。

下一次新开话题时，直接让 Codex 读取那个文件，它就能快速恢复上下文。

对于开发者来说，代码库本身其实就是项目记忆。AI 进入代码库之后，可以通过读代码知道业务是什么、结构是什么、接口怎么设计。

如果是团队协作，也可以接入飞书 CLI，让 Codex 读取或写入飞书云文档。这样云文档也可以成为团队共享记忆。

相比系统自动记忆，我更推荐这种文件化记忆方式。

因为它更透明、可控、可编辑，也更不容易污染上下文。

## 十三、为什么我不太建议开启自动 Memory

Codex 里也可以开启自带 Memory，但我个人不是特别建议大家默认打开。

原因是，目前很多 AI 的自动记忆功能都有一个问题：它经常会把一些无关紧要的信息写进去。

比如你只是对某一个项目说：“这个页面用浅蓝色配色。”
AI 可能会把它记成：“用户偏好浅蓝色配色。”

但这其实不是你的全局偏好，只是当前项目的需求。

时间长了之后，你可能根本不知道 Memory 里写了什么。它反而会在后续任务中造成干扰。

所以我更倾向于把重要信息写进文件里。

文件的好处是你能看见、能修改、能删除，也能明确告诉 AI 什么时候读取它。

## 十四、外观、个性化和工作模式设置

Codex 还有一些个性化设置，也值得调整。

在 Appearance 里面，可以设置字体、颜色、文字颜色、背景色等。

它还有一个宠物功能。我之前也玩过，甚至做过几个自定义宠物。不过后来我关掉了，因为它有点占屏幕空间。

在个性化设置里，可以选择 Codex 回复你的方式，比如更友好，或者更精简。

我自己会选择更友好的方式。因为 Codex 本身说话有时候比较偏工具化，我会希望它在解释时更容易看懂一些。

我也会加一些内置提示词，让它回答时补足上下文，不要只给结论，要让我能理解为什么这么做。

另外，在 General 里面还有一个 Work Mode，可以选择你主要是写代码，还是用于日常工作。

如果选择日常工作模式，它在执行任务时会展示更少代码相关信息，比如脚本执行过程、命令细节等。这样界面会更清爽，也更适合非开发者使用。

## 十五、防止电脑休眠：长任务一定要打开

还有一个非常实用的配置，就是防止 Codex 运行过程中电脑进入睡眠模式。

如果你经常让 Codex 跑长任务，比如写代码、跑调研、生成报告、执行自动化，那么一定要打开这个开关。

否则它执行到一半，电脑休眠了，任务可能就中断了。

这个配置在设置里可以找到，打开之后，Codex 执行任务时电脑就不会自动睡眠。

## 十六、最后总结

Codex 的使用方式，其实不只是“输入问题，让它回答”。

如果想真正把它用好，需要理解几个核心概念：

线程适合管理独立任务；
长期任务可以 pin 到顶部；
语音输入适合快速描述复杂需求；
队列和 steer 可以管理任务执行节奏；
浏览器工具适合网页自动化；
Computer Use 更适合作为兜底方案；
MCP 和 Skill 可以扩展外部能力；
Automation 适合定时任务；
Goals 适合长时间目标执行；
Side Panel 适合不污染主线程的临时追问；
文件化记忆比自动 Memory 更可控；
工作模式和防休眠配置能提升长期使用体验。

我现在越来越觉得，Codex 真正强的地方，不是单次问答，而是它能围绕项目、文件、工具和目标持续工作。

当你把线程、项目、文件、Skill、MCP、Automation 和 Goals 这些能力组合起来，它就不只是一个聊天机器人，而更像是一个可以长期协作的工作助手。
